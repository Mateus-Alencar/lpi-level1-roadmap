## 1. Visão geral e objetivos do tópico

Este tópico trata de **manter um sistema de arquivos saudável**. Na prática, um administrador precisa responder a três perguntas:

| Pergunta | O que fazer | Ferramentas |
|---|---|---|
| "Meu sistema de arquivos está **íntegro**?" | Verificar a consistência das estruturas internas | `fsck`, `e2fsck`, `xfs_repair -n` |
| "Ainda tenho **espaço** (blocos) e **inodes** livres?" | Monitorar uso | `df`, `du`, `df -i` |
| "Dá para **consertar** um problema simples?" | Reparar e ajustar | `fsck`, `e2fsck`, `tune2fs`, `dumpe2fs`, `debugfs`, `xfs_repair` |

### Objetivos oficiais (resumo)

- **Verificar a integridade** de sistemas de arquivos.
- **Monitorar espaço livre e inodes livres.**
- **Reparar problemas simples** em sistemas de arquivos.

### Arquivos, termos e utilitários citados pelo LPI

```
du  df  fsck  e2fsck  mke2fs  debugfs  dumpe2fs  tune2fs
ferramentas do XFS (xfs_repair, xfs_fsr, xfs_db, ...)
```

> 💡 **Dica de estudo:** o LPI cobra *o que cada comando faz*, *quais opções são mais importantes* e *em que situação usá-lo*. Decorar a sintaxe exata de tudo é menos importante do que entender o **fluxo lógico**: detectar → desmontar → verificar → reparar → revalidar.

## 2. Conceitos fundamentais

Antes dos comandos, é essencial entender o que está sendo "verificado". Sem isso, as opções do `fsck` parecem aleatórias.

### 2.1 O que é um sistema de arquivos?

É a **estrutura de dados** que o kernel usa para organizar arquivos em uma partição/volume. Ele precisa responder: *"onde, no disco, estão os bytes do arquivo X? Quem é o dono? Quais as permissões? Quais blocos estão livres?"*

### 2.2 Anatomia de um sistema de arquivos ext2/ext3/ext4

```
+-----------+---------------------------------------------------------------+
| Boot blk  |  Grupo de blocos 0  |  Grupo 1  |  Grupo 2  |  ...  | Grupo N |
+-----------+---------------------------------------------------------------+
                    |
                    v
   +------------+-------------------+--------------+--------------+-------------+--------------+
   | Superbloco | Descritores de    | Bitmap de    | Bitmap de    | Tabela de   | Blocos de    |
   | (+ cópias) | grupo (+ cópias)  | blocos       | inodes       | inodes      | DADOS        |
   +------------+-------------------+--------------+--------------+-------------+--------------+
```

| Componente | Função |
|---|---|
| **Superbloco** | "Certidão de nascimento" do FS: tipo, tamanho, tamanho do bloco, total de inodes/blocos, blocos livres, **estado (clean/not clean)**, contador de montagens, data da última checagem, features ativas. Se for corrompido, o FS não monta. |
| **Descritores de grupo** | Dizem onde estão os bitmaps e a tabela de inodes de cada grupo. |
| **Bitmap de blocos** | Mapa de bits: cada bit diz se um bloco de dados está livre (0) ou usado (1). |
| **Bitmap de inodes** | Idem, para inodes. |
| **Tabela de inodes** | Onde ficam os inodes. |
| **Blocos de dados** | O conteúdo real dos arquivos e diretórios. |

> 🔑 **Cópias do superbloco:** o superbloco e os descritores de grupo são **replicados** em alguns grupos de blocos (*backup superblocks*). É isso que permite recuperar um FS cujo superbloco primário foi danificado (seção 7).

### 2.3 Inode

O **inode** (*index node*) é a estrutura que guarda os **metadados** de um arquivo:

- tipo (arquivo, diretório, link simbólico, dispositivo...)
- permissões, dono (UID) e grupo (GID)
- tamanho
- timestamps (atime, mtime, ctime)
- contagem de links (*hard links*)
- **ponteiros para os blocos de dados**

⚠️ O inode **NÃO guarda o nome do arquivo**. O nome fica na **entrada de diretório**, que associa *nome → número do inode*.

```
Diretório /home/ana                   Tabela de inodes
+----------------+---------+          +----------+------------------------+
| nome           | inode # |          | inode #  | metadados + blocos     |
+----------------+---------+   --->   +----------+------------------------+
| relatorio.txt  | 52113   |          | 52113    | dono=ana, 4 KB, ...    |
| foto.png       | 52114   |          | 52114    | dono=ana, 2 MB, ...    |
+----------------+---------+          +----------+------------------------+
```

**Consequência crucial para o tópico:** em ext2/3/4 o **número de inodes é fixado no momento da criação** do sistema de arquivos. Você pode ter **espaço de sobra e mesmo assim não conseguir criar arquivos** porque os inodes acabaram (seção 4).

### 2.4 Blocos

Os dados são alocados em **blocos** (tipicamente 1 KB, 2 KB ou 4 KB). Um arquivo de 1 byte ocupa **pelo menos 1 bloco** (por isso `du` e o tamanho "aparente" podem diferir — seção 5).

### 2.5 Journaling (registro em diário)

Imagine gravar um arquivo: o kernel precisa atualizar o bitmap, o inode, o diretório e os dados. Se a energia cair no meio, o FS fica **inconsistente**.

O **journal** é uma área reservada onde o FS **anota o que vai fazer antes de fazer**:

```
1. Escreve no journal: "vou alterar X, Y, Z"
2. Executa as alterações no FS de verdade
3. Marca no journal: "concluído"
```

Após uma queda, basta **reexecutar (replay)** o que está no journal — operação rápida (segundos), mesmo em discos enormes.

| Sistema | Journal | Observações |
|---|---|---|
| **ext2** | ❌ Não | Após queda, `fsck` completo é obrigatório → lento |
| **ext3** | ✅ Sim | ext2 + journal |
| **ext4** | ✅ Sim | Padrão em muitas distros; extents, mais rápido |
| **XFS** | ✅ Sim (só metadados) | Padrão no RHEL/CentOS/Rocky/Alma |
| **Btrfs** | Copy-on-write (não usa journal clássico) | Checksums de dados e metadados |
| **FAT/VFAT** | ❌ Não | Pendrives, partição EFI |

**Modos de journaling do ext3/ext4** (opção de montagem `data=`):

| Modo | O que vai para o journal | Característica |
|---|---|---|
| `journal` | Metadados **e** dados | Mais seguro, mais lento |
| `ordered` (padrão) | Só metadados, mas dados são gravados **antes** | Bom equilíbrio |
| `writeback` | Só metadados, ordem dos dados não garantida | Mais rápido, menos seguro |

> ⚠️ **Journal não é backup nem elimina o `fsck`.** Ele protege contra inconsistência causada por **quedas/desligamentos súbitos**. Não protege contra defeito físico do disco, bugs de kernel, corrupção por hardware com problema, etc.

### 2.6 O que significa "estado limpo" (*clean*)

O superbloco tem um *flag* de estado:

- **clean**: o FS foi **desmontado corretamente** da última vez → o `fsck` normalmente **pula** a verificação.
- **not clean / dirty**: o FS estava montado quando o sistema caiu, ou erros foram detectados → o `fsck` **verifica**.

Quando você **monta** um FS para leitura/escrita, ele é marcado como "not clean". Ao **desmontar**, é marcado como "clean". Esse é o motivo de a verificação ser dispensável após um `shutdown` normal.

## 3. Monitorando espaço livre: `df` e `du`

Dois comandos com perguntas diferentes:

| Comando | Responde | Perspectiva |
|---|---|---|
| **`df`** (*disk free*) | "Quanto espaço **cada sistema de arquivos montado** tem usado/livre?" | **Do sistema de arquivos** (consulta o superbloco via `statfs`) |
| **`du`** (*disk usage*) | "Quanto espaço **estes arquivos/diretórios** ocupam?" | **Dos arquivos** (percorre a árvore somando) |

### 3.1 `df`

```bash
df [OPÇÕES] [ARQUIVO/DIRETÓRIO/DISPOSITIVO...]
```

Exemplo básico (blocos de 1 KB, difícil de ler):

```console
$ df
Filesystem     1K-blocks     Used Available Use% Mounted on
/dev/sda2       51474044 12345678  36491234  26% /
/dev/sda1         523248     5340    517908   2% /boot/efi
tmpfs            8123456        0   8123456   0% /dev/shm
```

Com `-h` (legível) e `-T` (tipo do FS):

```console
$ df -hT
Filesystem     Type   Size  Used Avail Use% Mounted on
/dev/sda2      ext4    49G   12G   35G  26% /
/dev/sda1      vfat   511M  5.3M  506M   2% /boot/efi
/dev/sdb1      xfs    100G   40G   60G  40% /dados
tmpfs          tmpfs  7.8G     0  7.8G   0% /dev/shm
```

#### Opções importantes do `df`

| Opção | Significado |
|---|---|
| `-h` | **Human-readable**: potências de **1024** (K, M, G) |
| `-H` | Idem, mas potências de **1000** (SI) |
| `-k` / `-m` | Força unidades de 1 KB / 1 MB |
| `-T` | Mostra o **tipo** do FS |
| `-i` | Mostra **inodes** (usados/livres) em vez de blocos |
| `-a` | Inclui FS "dummy" (proc, sysfs, ...) com 0 blocos |
| `-t TIPO` | **Só** mostra FS do tipo indicado (`-t ext4`) |
| `-x TIPO` | **Exclui** FS do tipo indicado (`-x tmpfs`) |
| `-l` | Só FS **locais** (exclui NFS etc.) |
| `--total` | Adiciona linha de total |
| `--output=campos` | Escolhe colunas (`source,fstype,size,used,avail,pcent,itotal,iused,ipcent,target`) |

```console
# Só ext4 e xfs, de forma legível:
$ df -h -t ext4 -t xfs

# Em qual FS está determinado arquivo/diretório?
$ df -h /var/log/syslog
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda2        49G   12G   35G  26% /

# Ocultar pseudo-sistemas
$ df -hx tmpfs -x devtmpfs
```

> 💡 **`df` com um caminho** é ótimo para descobrir **a qual partição** um diretório pertence (útil ao investigar "disco cheio").

#### Entendendo as colunas

| Coluna | Significado |
|---|---|
| `Filesystem` | Dispositivo (ou fonte) |
| `Size` | Tamanho total **utilizável** (já descontadas estruturas internas do FS) |
| `Used` | Usado |
| `Avail` | **Disponível para usuários comuns** |
| `Use%` | `Used / (Used + Avail)` |
| `Mounted on` | Ponto de montagem |

🔎 **Detalhe sutil:** em ext2/3/4, por padrão **5% dos blocos são reservados para o root** (para que o sistema continue funcionando e a fragmentação seja menor). Por isso **`Size ≠ Used + Avail`**: a diferença é o espaço reservado. Isso se ajusta com `tune2fs -m` (seção 9).

### 3.2 `du`

```bash
du [OPÇÕES] [ARQUIVO/DIRETÓRIO...]
```

Sem argumentos, percorre o diretório atual **recursivamente** e imprime o tamanho de **cada subdiretório** (em blocos de 1 KB por padrão):

```console
$ du /var/log
4       /var/log/apt
120     /var/log/journal/abcdef
...
2048    /var/log
```

#### Opções importantes do `du`

| Opção | Significado |
|---|---|
| `-h` | Legível (K, M, G, base 1024) |
| `-s` | **Summarize**: só o **total** de cada argumento |
| `-a` | Mostra também **arquivos**, não só diretórios |
| `-c` | Adiciona linha com **total geral** |
| `-d N` / `--max-depth=N` | Limita a profundidade da listagem |
| `-x` | **Não cruza** para outros sistemas de arquivos (`--one-file-system`) |
| `-S` | Não inclui o tamanho de subdiretórios no total do diretório pai |
| `-L` | Segue links simbólicos |
| `--apparent-size` | Mostra o **tamanho aparente** (bytes lógicos), não o uso em disco |
| `-b` | Equivale a `--apparent-size --block-size=1` |
| `-k`, `-m` | Unidades de KB / MB |
| `--exclude=PADRÃO` | Ignora arquivos que casam com o padrão |
| `--time` | Mostra a data da última modificação |
| `-t TAM` / `--threshold=TAM` | Ignora entradas menores (ou, se negativo, maiores) que TAM |

#### Receitas úteis

```bash
# Tamanho total de um diretório
du -sh /var/log

# Quem ocupa mais espaço dentro de /var? (1 nível, ordenado)
du -h --max-depth=1 /var | sort -h

# Os 10 maiores diretórios/arquivos sem sair da partição raiz
du -ahx / 2>/dev/null | sort -rh | head -n 10

# Total de vários itens + total geral
du -shc /etc /var/log /home

# Excluindo arquivos temporários
du -sh --exclude='*.tmp' /dados
```

> ⚠️ `sort -h` entende sufixos (K/M/G). Sem `-h`, a ordenação de `4.0K`, `1.2G`, `300M` fica errada. Combine `du -h` com `sort -h`.

## 4. Monitorando inodes

### 4.1 O problema

Cada arquivo, diretório, link simbólico ou socket **consome 1 inode**. Se os inodes acabam, você recebe:

```console
$ touch novo.txt
touch: cannot touch 'novo.txt': No space left on device
```

...**mesmo com `df -h` mostrando espaço livre!** É o clássico caso de **esgotamento de inodes**, comum em diretórios com milhões de arquivos minúsculos (filas de e-mail, sessões PHP, cache, logs em excesso).

### 4.2 Como detectar: `df -i`

```console
$ df -i
Filesystem      Inodes   IUsed   IFree IUse% Mounted on
/dev/sda2      3276800  3276800       0  100% /
/dev/sdb1      6553600    52113 6501487    1% /dados
```

Colunas: `Inodes` (total), `IUsed`, `IFree`, `IUse%`.

> 🧠 Sempre que ouvir *"No space left on device"* mas `df -h` mostra espaço livre → **rode `df -i`**.

### 4.3 Como encontrar o culpado

```bash
# Contar entradas (arquivos+dirs) por diretório de primeiro nível, sem cruzar FS
for d in /var/*; do echo "$(find "$d" -xdev 2>/dev/null | wc -l) $d"; done | sort -n

# Ver o número do inode de um arquivo
ls -i arquivo.txt

# Informações completas do inode
stat arquivo.txt

# Informações do FS (inclusive inodes totais/livres)
stat -f /
```

### 4.4 Como resolver

1. **Remover** arquivos desnecessários (ex.: sessões antigas, cache, filas travadas).
2. Se o problema é estrutural: **recriar** o FS com mais inodes (`mke2fs -N` ou `-i`, seção 12) e restaurar os dados — **não dá para aumentar o número de inodes de um ext4 já criado** (o `resize2fs` aumenta proporcionalmente ao crescer o FS, mas não é o ajuste fino do `-N`).
3. Em **XFS** e **Btrfs** os inodes são **alocados dinamicamente** (XFS limita por um percentual do FS, `imaxpct`), então esgotamento é bem mais raro.

| FS | Inodes |
|---|---|
| ext2/3/4 | **Fixos** na criação |
| XFS | **Dinâmicos** (limite por `imaxpct`) |
| Btrfs | **Dinâmicos** |

## 5. Por que `df` e `du` mostram valores diferentes?

É uma das dúvidas mais frequentes — e uma ótima pergunta de entrevista/prova.

### 5.1 Causas comuns

| Causa | Explicação |
|---|---|
| **Arquivos apagados mas ainda abertos** | O arquivo foi removido (`rm`), mas um processo mantém o descritor aberto. O nome sumiu (o `du` não o enxerga), porém **os blocos só são liberados quando o processo fecha o arquivo**. O `df` continua mostrando o espaço ocupado. |
| **Blocos reservados (5% no ext)** | `df` considera o espaço reservado ao root. |
| **Metadados e journal** | Inodes, bitmaps, journal consomem espaço que **não aparece como arquivo** para o `du`. |
| **Ponto de montagem "escondendo" dados** | Se você montou um FS sobre um diretório que **já tinha arquivos**, esses arquivos continuam ocupando espaço na partição de baixo, mas ficam **invisíveis** (e o `du` não os vê). |
| **Tamanho aparente x uso real** | Arquivos **esparsos** (*sparse*) têm tamanho aparente grande mas ocupam poucos blocos. Arquivos pequenos ocupam um bloco inteiro. |
| **`du` sem permissão** | Sem root, o `du` não consegue entrar em certos diretórios e subestima o total. |
| **Snapshots/subvolumes** (Btrfs, LVM thin) | Espaço compartilhado/retido não aparece como arquivos. |

### 5.2 Caso clássico: arquivo de log apagado, disco continua cheio

```console
$ df -h /var
/dev/sda3   20G   20G     0 100% /var

$ du -sh /var
8.2G    /var                      # ← onde estão os outros 12 GB?!

# Lista arquivos apagados mas ainda abertos (link count = 0):
$ sudo lsof +L1
COMMAND   PID USER   FD   TYPE DEVICE   SIZE/OFF NLINK NODE NAME
java     2211 app    5w   REG    8,3  12884901888     0  131 /var/log/app.log (deleted)
```

**Soluções:**

```bash
# a) Reiniciar o processo (libera o descritor → libera os blocos)
sudo systemctl restart app

# b) Sem reiniciar: truncar o arquivo através do /proc
sudo truncate -s 0 /proc/2211/fd/5        # (ou: : > /proc/2211/fd/5 como root)
```

> 💡 **Boa prática:** para esvaziar um log em uso, **não use `rm`**; use `truncate -s 0 arquivo` ou `> arquivo` (ou deixe o `logrotate` fazer o trabalho).

### 5.3 Caso: dados "escondidos" sob um ponto de montagem

```bash
# Faz um bind mount da raiz num diretório auxiliar para enxergar o que há "por baixo"
sudo mount --bind / /mnt/raiz
sudo du -sh /mnt/raiz/dados     # mostra o que estava no diretório antes da montagem
sudo umount /mnt/raiz
```

## 6. Verificando e reparando: `fsck` e `e2fsck`

### 6.1 O que é o `fsck`

**`fsck`** (*file system check*) é a ferramenta de **verificação e reparo de consistência**. Ele **não é um único programa**, e sim um **"front-end"** (*wrapper*) que identifica o tipo do FS e chama o utilitário específico:

```
fsck  ──►  fsck.ext2 / fsck.ext3 / fsck.ext4   (= links para e2fsck)
      ──►  fsck.xfs        (não faz nada! veja seção 13)
      ──►  fsck.vfat / fsck.fat  (= dosfsck)
      ──►  fsck.btrfs      (não faz nada! use btrfs check)
```

```console
$ ls -l /sbin/fsck.*
lrwxrwxrwx 1 root root 6 ... /sbin/fsck.ext4 -> e2fsck
lrwxrwxrwx 1 root root 6 ... /sbin/fsck.ext3 -> e2fsck
```

> 🔑 **`e2fsck`** é o verificador **nativo da família ext2/3/4**. `fsck -t ext4 /dev/sdb1` ≡ `fsck.ext4 /dev/sdb1` ≡ `e2fsck /dev/sdb1`.

### 6.2 ⚠️ REGRA DE OURO

> **Nunca execute `fsck` em um sistema de arquivos MONTADO (em leitura/escrita).**
>
> O kernel pode estar alterando as mesmas estruturas que o `fsck` está "consertando" → **corrupção severa**. O `e2fsck` até avisa:
>
> `WARNING!!! The filesystem is mounted. If you continue you ***WILL*** cause ***SEVERE*** filesystem damage.`

Ou seja: **desmonte antes** (`umount`). Para o sistema raiz `/`, use um dos métodos da seção 8.3 (modo de recuperação, live CD, verificação na inicialização).

### 6.3 Sintaxe do `fsck` genérico

```bash
fsck [opções-do-fsck] [-t tipo] [dispositivo...] -- [opções-do-verificador-específico]
```

#### Opções do `fsck` (front-end)

| Opção | Significado |
|---|---|
| `-t tipo` | Tipo do FS (`ext4`, `xfs`, `vfat`...). Se omitido, o `fsck` consulta `/etc/fstab` / `blkid`. |
| `-A` | Verifica **todos** os FS listados em `/etc/fstab` (usado na inicialização) |
| `-R` | Com `-A`, **pula o raiz** (`/`) — útil quando `/` já está montado rw |
| `-P` | Com `-A`, verifica vários FS **em paralelo** |
| `-s` | **Serializa** (um por vez) |
| `-N` | **Dry-run**: só mostra o que seria executado, **não executa** |
| `-V` | *Verbose* |
| `-T` | Não exibe o cabeçalho/versão |
| `-C [fd]` | Mostra **barra de progresso** (ext) |
| `-M` | **Não** verifica FS que estejam **montados** |

#### Opções repassadas ao `e2fsck` (muito cobradas)

| Opção | Significado | Observação |
|---|---|---|
| `-p` | **Preen** (modo automático "seguro"): corrige **só problemas triviais**, sem perguntar; se encontrar algo grave, **para** e exige execução manual | Usado na inicialização. Substitui o antigo `-a` |
| `-a` | Igual a `-p` (mantido por compatibilidade, **desencorajado**) | |
| `-n` | **Somente leitura**: abre o FS read-only e responde **"não"** a tudo. **Nada é alterado** | Ótimo para "ver o tamanho do estrago" |
| `-y` | Responde **"sim"** a **todas** as perguntas | Rápido, mas **arriscado** |
| `-f` | **Força** a verificação mesmo que o FS esteja marcado como *clean* | Essencial para verificar de verdade |
| `-b N` | Usa o **superbloco de backup** no bloco N (seção 7) | |
| `-B tam` | Informa o tamanho do bloco ao procurar superbloco | |
| `-c` | Executa `badblocks` e marca blocos defeituosos | Lento |
| `-D` | **Otimiza diretórios** (reindexa/compacta) | |
| `-v` | *Verbose* (estatísticas) | |
| `-C 0` | Barra de progresso | |

> 🧠 **`-p`, `-n` e `-y` são mutuamente exclusivos.** Só pode usar um.

### 6.4 As 5 fases (passes) do `e2fsck`

Ao verificar um ext2/3/4 com `-f`, você verá algo assim:

```console
$ sudo e2fsck -f /dev/sdb1
e2fsck 1.46.5 (30-Dec-2021)
Pass 1: Checking inodes, blocks, and sizes
Pass 2: Checking directory structure
Pass 3: Checking directory connectivity
Pass 4: Checking reference counts
Pass 5: Checking group summary information
/dev/sdb1: 11/655360 files (0.0% non-contiguous), 66753/2621440 blocks
```

| Fase | O que verifica | Problemas típicos |
|---|---|---|
| **1** | **Inodes, blocos e tamanhos** | Blocos duplicados (dois arquivos "donos" do mesmo bloco), blocos fora do intervalo válido, tamanho incoerente |
| **2** | **Estrutura de diretórios** | Entradas que apontam para inodes inválidos/livres, nomes corrompidos |
| **3** | **Conectividade de diretórios** | Diretórios "órfãos" (sem pai) → são ligados em `lost+found` |
| **4** | **Contagem de referências (links)** | Inode com contagem de links errada; **inodes não referenciados** (arquivo existe mas nenhum diretório aponta para ele) → vão para `lost+found` |
| **5** | **Informações de resumo dos grupos** | Bitmaps de blocos/inodes e contadores de livres inconsistentes |

> 📌 **Decore a ordem:** 1 Inodes/Blocos/Tamanhos → 2 Diretórios → 3 Conectividade → 4 Referências (links) → 5 Resumo dos grupos.

### 6.5 Mensagens/perguntas típicas

Em modo interativo (sem `-p`/`-y`), o `e2fsck` pergunta, por exemplo:

```
Inode 12345 has illegal blocks.  Clear<y>?
Entry 'foo' in /dir (2) has deleted/unused inode 99.  Clear<y>?
Unattached inode 4321
Connect to /lost+found<y>?
Free blocks count wrong for group #3 (100, counted=98).  Fix<y>?
```

Responder **`y`** = aplicar a correção; **`n`** = ignorar.

### 6.6 Códigos de saída (exit status)

O código de saída é a **soma (bit a bit)** dos valores abaixo — muito útil em scripts e cobrado em prova.

| Valor | Significado |
|---|---|
| **0** | Nenhum erro |
| **1** | Erros foram **corrigidos** |
| **2** | Erros foram corrigidos e o **sistema deve ser reiniciado** |
| **4** | Erros **não corrigidos** (ainda há problemas) |
| **8** | Erro operacional |
| **16** | Erro de uso ou de sintaxe |
| **32** | `fsck` **cancelado** pelo usuário |
| **128** | Erro em biblioteca compartilhada |

Exemplo: saída **3** = 1 + 2 → erros corrigidos **e** reinício necessário.

```bash
sudo fsck -fp /dev/sdb1
echo $?        # ← código de saída do último comando
```

### 6.7 Exemplos práticos

```bash
# 1) Desmontar e verificar (forçando) um ext4
sudo umount /dev/sdb1
sudo fsck -f /dev/sdb1                 # interativo
sudo fsck.ext4 -f /dev/sdb1            # equivalente (usa e2fsck direto)

# 2) Só "olhar", sem alterar nada (dry-run do reparo)
sudo e2fsck -fn /dev/sdb1

# 3) Reparar tudo automaticamente respondendo "sim" (cuidado!)
sudo e2fsck -fy /dev/sdb1

# 4) Modo automático "seguro" (preen)
sudo e2fsck -fp /dev/sdb1

# 5) Ver o que o fsck faria para TODOS os FS do fstab, sem executar
sudo fsck -AN

# 6) Verificar todos, menos o raiz, com progresso
sudo fsck -ARC

# 7) Forçar checagem + otimizar diretórios
sudo e2fsck -fD /dev/sdb1
```

> 💡 **Boa prática:** rode **primeiro** `e2fsck -fn` para avaliar a gravidade; só depois decida entre `-p`, interativo ou `-y`. Em caso de dados críticos, **faça uma imagem/backup do dispositivo** antes (`dd` / `ddrescue`).

## 7. Superblocos de backup e o diretório `lost+found`

### 7.1 Superbloco corrompido

Sintomas ao montar/verificar:

```
mount: wrong fs type, bad option, bad superblock on /dev/sdb1
e2fsck: Bad magic number in super-block while trying to open /dev/sdb1
The superblock could not be read or does not describe a valid ext2/ext3/ext4 filesystem.
```

O ext mantém **cópias** do superbloco em grupos de blocos específicos. Usando uma cópia, o `e2fsck` reconstrói o primário.

### 7.2 Onde estão os backups?

Posições **típicas** (dependem do tamanho do bloco):

| Tamanho do bloco | Backups do superbloco (blocos) |
|---|---|
| **1 KB** | 8193, 24577, 40961, 57345, 73729, ... |
| **4 KB** | **32768**, 98304, 163840, 229376, 294912, ... |

Para **descobrir** com certeza:

```bash
# a) dumpe2fs lista os superblocos de backup (se o primário ainda for legível)
sudo dumpe2fs /dev/sdb1 | grep -i superblock
  Primary superblock at 0, Group descriptors at 1-1
  Backup superblock at 32768, Group descriptors at 32769-32769
  Backup superblock at 98304, Group descriptors at 98305-98305

# b) mke2fs -n  (dry-run: NÃO cria nada, só mostra onde estariam)
#    ⚠ use os MESMOS parâmetros (tipo, -b, etc.) com que o FS foi criado
sudo mke2fs -n /dev/sdb1
```

### 7.3 Reparando com o superbloco de backup

```bash
sudo e2fsck -b 32768 /dev/sdb1
# opcionalmente informando o tamanho do bloco:
sudo e2fsck -b 8193 -B 1024 /dev/sdb1
```

Após usar o backup, o `e2fsck` **regrava o superbloco primário** com os dados da cópia.

> ⚠️ `mke2fs -n` é só *dry-run*. **Sem o `-n`, o `mke2fs` RECRIA o sistema de arquivos e APAGA tudo.**

### 7.4 O diretório `lost+found`

- Existe na **raiz de cada FS ext** (e é criado pelo `mke2fs`).
- É onde o `e2fsck` coloca **arquivos/diretórios recuperados sem nome** (inodes "órfãos": nenhuma entrada de diretório aponta para eles).
- Os itens aparecem **nomeados pelo número do inode**: `#12345`, `#12346`...

```console
$ ls -l /mnt/dados/lost+found
-rw-r--r-- 1 ana ana 14213 ... #52113
drwxr-xr-x 2 ana ana  4096 ... #52200
```

**Como identificar o que foi recuperado:**

```bash
file '/mnt/dados/lost+found/#52113'     # tipo do conteúdo (texto, JPEG, ELF...)
stat '/mnt/dados/lost+found/#52113'     # dono, datas, tamanho
head '/mnt/dados/lost+found/#52113'     # espiar o conteúdo
```

Depois, mova de volta com um nome adequado (`mv`).

**Detalhes importantes:**

- O diretório `lost+found` tem **blocos pré-alocados**, para que o `e2fsck` consiga inserir entradas **mesmo com o FS 100% cheio**. Por isso **não o apague**. Se apagar por engano: `mklost+found` (dentro do FS montado) ou `e2fsck` recria.
- Em **XFS** não existe `lost+found` da mesma forma; o `xfs_repair` cria `lost+found` **se necessário**, quando há arquivos desconectados.

## 8. Verificação automática na inicialização

### 8.1 `/etc/fstab` — os 6 campos

```
# <dispositivo>            <ponto>   <tipo>  <opções>   <dump>  <pass>
UUID=1a2b3c4d-...          /         ext4    defaults     0       1
UUID=5e6f7a8b-...          /boot     ext4    defaults     0       2
UUID=9c0d1e2f-...          /dados    xfs     defaults     0       0
```

O **6º campo (`fs_passno` / "pass")** controla a ordem de checagem no boot:

| Valor | Significado |
|---|---|
| **0** | **Não verifica** esse FS no boot (use para **XFS**, Btrfs, tmpfs, NFS...) |
| **1** | Verificado **primeiro**. **Reservado para o `/` (raiz)** |
| **2** | Verificado **depois** do raiz. Para os demais FS |

FS com o **mesmo número** de pass em **discos diferentes** podem ser verificados **em paralelo**.

O **5º campo (`dump`)**: `0` = ignorado pelo utilitário `dump` (backup); `1` = incluído.

### 8.2 Como a verificação é decidida

No boot, para cada FS com pass ≠ 0, a verificação roda (`fsck -p` / preen) **se**:

1. O FS está **marcado como "not clean"**; **ou**
2. O **contador de montagens** atingiu o máximo (`tune2fs -c`); **ou**
3. O **intervalo de tempo** entre verificações expirou (`tune2fs -i`); **ou**
4. A verificação foi **forçada** (seção 8.3).

Em distribuições com **systemd**, quem executa isso é o `systemd-fsck@.service` (instanciado por dispositivo). Se o `fsck -p` encontrar algo grave, o sistema cai em **modo de emergência** (*emergency shell*), pedindo a senha de root para manutenção manual.

### 8.3 Verificando o sistema de arquivos raiz (`/`)

Como **não dá para desmontar `/`** em um sistema em execução, as alternativas são:

| Método | Como |
|---|---|
| **Forçar no próximo boot (systemd)** | Adicionar ao kernel (no GRUB) `fsck.mode=force` (opcionalmente `fsck.repair=yes` para responder sim a tudo, ou `fsck.repair=preen`) |
| **Forçar no próximo boot (SysV legado)** | `touch /forcefsck` ou `shutdown -rF now` |
| **Modo de recuperação/emergência** | Boot em *rescue/single* e executar o `fsck` com `/` ainda **somente leitura** |
| **Live CD/USB ou disco de resgate** | Boot por mídia externa e `fsck` no dispositivo do `/` (desmontado) |
| **Remontar como somente leitura** | `mount -o remount,ro /` e então `e2fsck -fn /dev/xxx` (somente análise; evite reparar assim) |

```bash
# Exemplo: parâmetros adicionados na linha do kernel no GRUB (tecla 'e')
linux /vmlinuz-... root=/dev/sda2 ro fsck.mode=force fsck.repair=yes
```

> 🔎 Parâmetros do kernel/systemd: `fsck.mode=auto|force|skip` e `fsck.repair=preen|yes|no`. Também há `fastboot` / `forcefsck` (legado) na linha de comando.

### 8.4 O que acontece com FS XFS no boot?

O XFS **não precisa** de `fsck` no boot: após queda, o **log é reexecutado na montagem**. Por isso `fsck.xfs` é um programa "vazio" (`exit 0`) e o `pass` costuma ser **0** no `fstab`. Veja seção 13.

## 9. Ajustando parâmetros: `tune2fs`

`tune2fs` **ajusta parâmetros ajustáveis** do superbloco de um **ext2/3/4**.

```bash
tune2fs [opções] dispositivo
```

> Algumas opções funcionam com o FS montado; outras exigem desmontado. Em caso de dúvida, **desmonte**.

### 9.1 Listar parâmetros (`-l`)

```console
$ sudo tune2fs -l /dev/sdb1
tune2fs 1.46.5 (30-Dec-2021)
Filesystem volume name:   dados
Last mounted on:          /dados
Filesystem UUID:          a1b2c3d4-e5f6-7890-abcd-ef1234567890
Filesystem features:      has_journal ext_attr resize_inode dir_index filetype extent ...
Filesystem state:         clean
Errors behavior:          Continue
Inode count:              655360
Block count:              2621440
Reserved block count:     131072
Free blocks:              2554687
Free inodes:              655349
Block size:               4096
Mount count:              12
Maximum mount count:      -1
Last checked:             Mon Oct  5 10:12:03 2026
Check interval:           0 (<none>)
```

Campos de interesse para o tópico: **Filesystem state** (clean/not clean), **Errors behavior**, **Mount count**, **Maximum mount count**, **Last checked**, **Check interval**, **Reserved block count**.

### 9.2 Opções mais importantes

| Opção | Efeito |
|---|---|
| `-l` | **Lista** o conteúdo do superbloco |
| `-c N` | Define o **máximo de montagens** antes de forçar `fsck` (`-c 0` ou `-c -1` **desativa**) |
| `-C N` | Define o **contador atual** de montagens |
| `-i intervalo` | Intervalo **máximo de tempo** entre verificações: `d` (dias), `w` (semanas), `m` (meses). `-i 0` **desativa** |
| `-T data` | Define a data da última verificação (`now`) |
| `-e ação` | Comportamento em **erro**: `continue`, `remount-ro`, `panic` |
| `-m %` | **Percentual** de blocos **reservados** ao root (padrão 5%) |
| `-r N` | Número **absoluto** de blocos reservados |
| `-u usuário` / `-g grupo` | Quem pode usar os blocos reservados |
| `-L rótulo` | Define o **label** (rótulo) |
| `-U UUID` | Altera o **UUID** (`clear`, `random`, `time` ou valor) |
| `-j` | **Adiciona journal** (converte ext2 → ext3) |
| `-O feature` | Liga/desliga **features** (`-O has_journal`, `-O ^has_journal`) |
| `-o opções` | Define **opções de montagem padrão** |

### 9.3 Exemplos

```bash
# Desativar checagens periódicas por contagem e por tempo
sudo tune2fs -c 0 -i 0 /dev/sdb1

# Forçar fsck a cada 30 montagens OU a cada 3 meses (o que vier primeiro)
sudo tune2fs -c 30 -i 3m /dev/sdb1

# Em caso de erro, remontar como somente-leitura (evita agravar a corrupção)
sudo tune2fs -e remount-ro /dev/sdb1

# Reduzir reserva para 1% (comum em volumes de DADOS grandes; no / mantenha ~5%)
sudo tune2fs -m 1 /dev/sdb1

# Converter ext2 em ext3 (adiciona journal)
sudo tune2fs -j /dev/sdb1

# Alterar o rótulo
sudo tune2fs -L backup /dev/sdb1

# Forçar fsck no PRÓXIMO boot: coloca contador acima do máximo
sudo tune2fs -c 1 /dev/sdb1          # (máx. = 1)
sudo tune2fs -C 2 /dev/sdb1          # (contador atual = 2 > máx.)
```

### 9.4 `errors=` — comportamento em caso de erro (importante)

| Valor | Ação ao detectar erro no FS |
|---|---|
| `continue` | Ignora e continua (padrão em muitos casos) |
| `remount-ro` | **Remonta como somente leitura** — evita piorar a corrupção; é o comportamento mais comum em servidores |
| `panic` | **Kernel panic** (útil em clusters/HA, onde o nó deve cair e ser substituído) |

Também pode ser definido como **opção de montagem** (`mount -o errors=remount-ro`) e no `/etc/fstab`.

> 🧠 Sintoma clássico: do nada, a aplicação grava "Read-only file system". Quase sempre o kernel detectou erro de I/O/FS e **remontou em somente leitura** (`errors=remount-ro`). Verifique `dmesg` e rode o `fsck` com o FS desmontado.

## 11. Depurando: `debugfs`

`debugfs` é um **depurador interativo** de ext2/3/4. Permite **examinar** (e, com `-w`, **alterar**) estruturas internas: inodes, diretórios, blocos.

```bash
debugfs [opções] [dispositivo]
```

| Opção | Efeito |
|---|---|
| (padrão) | Abre em **somente leitura** (seguro) |
| `-w` | Abre em **leitura/escrita** (perigoso!) |
| `-c` | Modo "catastrófico": abre sem ler bitmaps/inode tables (para FS muito danificado) |
| `-R "comando"` | Executa **um** comando e sai |
| `-f arquivo` | Executa comandos de um arquivo |
| `-b N` / `-s N` | Tamanho de bloco / superbloco de backup |

### Comandos úteis dentro do `debugfs`

| Comando | O que faz |
|---|---|
| `stats` | Mostra informações do superbloco/grupos |
| `ls [-l] [dir]` | Lista diretório (inclui **entradas apagadas** com `-d`) |
| `cd dir` | Muda de diretório (dentro do FS) |
| `stat arquivo` ou `stat <inode>` | **Inode completo** (dono, tamanho, blocos, timestamps) |
| `ncheck inode` | **Inode → nome** do arquivo |
| `icheck bloco` | **Bloco → inode** que o usa |
| `blocks arquivo` | Lista os **blocos** de um arquivo |
| `dump arquivo saída` | **Copia** um arquivo do FS para o sistema "real" |
| `rdump dir destino` | Copia um **diretório** recursivamente |
| `cat arquivo` | Exibe o conteúdo |
| `lsdel` | Lista **inodes apagados** recentemente (ext2) |
| `undel <inode> arq` | **Recupera** um arquivo apagado (ext2) |
| `testb bloco` / `testi <inode>` | Testa se bloco/inode está **em uso** |
| `logdump` | Exibe o conteúdo do **journal** |
| `features` | Lista/altera features |
| `quit` | Sai |

```console
$ sudo debugfs /dev/sdb1
debugfs 1.46.5 (30-Dec-2021)
debugfs:  stat /relatorio.txt
Inode: 12   Type: regular    Mode:  0644   Flags: 0x80000
User:  1000   Group:  1000   Size: 14213
...
debugfs:  ncheck 12
Inode   Pathname
12      //relatorio.txt
debugfs:  quit

# Executando um único comando:
$ sudo debugfs -R "stats" /dev/sdb1 | head
```

### Sobre recuperar arquivos apagados

- Em **ext2** (sem journal), `lsdel` + `undel` podem recuperar arquivos recém-apagados **se os blocos não foram reaproveitados**.
- Em **ext3/ext4**, ao apagar, o kernel **zera os ponteiros de bloco do inode** (e usa *extents*), tornando a recuperação por `undel` **praticamente inviável**. Existem ferramentas especializadas (`extundelete`, `testdisk`, `photorec`), mas **a melhor "recuperação" é o backup**.
- Regra: **pare de usar o FS** (desmonte/remonte ro) assim que perceber a exclusão acidental, para não sobrescrever blocos.

> ⚠️ Usar `debugfs -w` sem saber exatamente o que faz pode **destruir** o sistema de arquivos. Para o exame LPIC-1, saiba **o que ele é e para que serve**, sem precisar dominar todos os comandos.

## 12. Criando sistemas ext: `mke2fs`

`mke2fs` **cria** (formata) um sistema de arquivos **ext2/3/4**. É o programa por trás de `mkfs.ext2`, `mkfs.ext3` e `mkfs.ext4`.

```
mkfs.ext4 /dev/sdb1   ≡   mke2fs -t ext4 /dev/sdb1   ≡   mkfs -t ext4 /dev/sdb1
```

> 📌 A criação de partições e sistemas de arquivos é aprofundada no **tópico 104.1**. Aqui interessa o `mke2fs` pelo seu papel na **integridade** (superblocos de backup) e **inodes**.

### 12.1 Opções importantes

| Opção | Efeito |
|---|---|
| `-t tipo` | `ext2`, `ext3` ou `ext4` |
| `-j` | Cria **com journal** (ext3) |
| `-b tam` | **Tamanho do bloco** (1024, 2048, 4096...) |
| `-i bytes` | **Razão bytes-por-inode**: 1 inode a cada N bytes de espaço. **Menor valor → mais inodes** |
| `-N num` | Define o **número exato de inodes** |
| `-m %` | **Percentual reservado** ao root (padrão 5%) |
| `-L rótulo` | Define o **label** |
| `-U UUID` | Define o UUID |
| `-O feat` | Features (`^has_journal` para desligar) |
| `-T tipo` | **Perfil de uso** (`small`, `floppy`, `news`, `largefile`, `largefile4`...) — ajusta inodes/bloco |
| `-c` | Verifica **bad blocks** antes de formatar |
| **`-n`** | **Dry-run**: **não grava nada**; apenas mostra o que faria (inclusive **onde ficariam os superblocos de backup**) |

### 12.2 Equilíbrio inodes × espaço

```bash
# Muitos arquivos pequenos (e-mail, cache): mais inodes (1 inode a cada 4 KB)
sudo mke2fs -t ext4 -i 4096 /dev/sdb1

# Poucos arquivos gigantes (vídeo, backup): menos inodes → sobra mais espaço útil
sudo mke2fs -t ext4 -T largefile4 /dev/sdb1

# Número exato de inodes
sudo mke2fs -t ext4 -N 2000000 /dev/sdb1
```

## 13. Sistemas de arquivos XFS

O **XFS** é o FS padrão do **RHEL/CentOS/Rocky/AlmaLinux** (e muito usado em servidores com arquivos grandes). Tem **ferramentas próprias** — o LPI cobra que você saiba que **`fsck` não é o caminho** para XFS.

### 13.1 Particularidades

- **Journaling** apenas de **metadados**.
- Após queda, o **log é reproduzido automaticamente ao montar** o FS.
- `fsck.xfs` **existe, mas não faz nada** (apenas retorna sucesso) — é só para não quebrar o fluxo do boot. Use **pass = 0** no `fstab`.
- Para checar/reparar de verdade: **`xfs_repair`** com o FS **desmontado**.
- Inodes **dinâmicos**.
- Um FS XFS pode ser **aumentado** (`xfs_growfs`), mas **não reduzido**.

### 13.2 Ferramentas XFS

| Ferramenta | Função | Observações |
|---|---|---|
| **`xfs_repair`** | **Verifica e repara** | **Desmontado**. `-n` = *no modify* (só verifica); `-L` = **zera o log** (último recurso); `-v` verbose |
| **`xfs_db`** | **Depurador** (equivalente ao `debugfs`) | `-r` somente leitura; `-x` modo "expert" (escrita) |
| **`xfs_fsr`** | **Desfragmenta** (*file system reorganizer*) | Pode rodar com FS **montado** |
| **`xfs_info`** | Mostra a **geometria** (blocos, inodes, log) | FS **montado** (`xfs_info /ponto`) |
| **`xfs_admin`** | Altera **label** (`-L`) e **UUID** (`-U`) | FS desmontado |
| **`xfs_growfs`** | **Expande** o FS | **Montado** |
| **`xfs_metadump`** | Exporta **metadados** para análise | Suporte/diagnóstico |
| **`xfs_freeze`** | **Congela** I/O (p/ snapshots) | `-f` congela, `-u` descongela (ou `fsfreeze`) |
| `xfs_check` | Verificador **antigo, obsoleto** | Substituído por `xfs_repair -n` |

### 13.3 Fluxo de reparo em XFS

```bash
# 1) Desmontar
sudo umount /dados

# 2) Somente verificar (nada é alterado)
sudo xfs_repair -n /dev/sdb1

# 3) Reparar
sudo xfs_repair /dev/sdb1
```

Se o log estiver "sujo" e o `xfs_repair` recusar, ele diz:

```
ERROR: The filesystem has valuable metadata changes in a log which needs to
be replayed.  Mount the filesystem to replay the log, and unmount it before
re-running xfs_repair.  If you are unable to mount the filesystem, then use
the -L option to destroy the log and attempt a repair.
```

**Ordem correta:**

1. **Tente montar e desmontar** (isso reproduz o log): `mount /dev/sdb1 /mnt && umount /mnt`.
2. Rode `xfs_repair` novamente.
3. **Só se não for possível montar**, use `xfs_repair -L` — **zera o log e pode perder as últimas alterações**; é **último recurso**.

```bash
sudo xfs_info /dados      # geometria (montado)
sudo xfs_fsr /dados       # desfragmentar
sudo xfs_db -r /dev/sdb1  # depurador (somente leitura)
```

## 14. Outros sistemas de arquivos: Btrfs e FAT

### 14.1 Btrfs (conhecimento complementar)

- **Copy-on-write**, **checksums** em dados e metadados, snapshots, subvolumes.
- **Não use** `fsck` no boot: `fsck.btrfs` não faz nada (pass = 0).

| Comando | Função |
|---|---|
| `btrfs check /dev/sdX` | Verifica (**desmontado**). `--repair` é **perigoso** — só como último recurso e com backup |
| `btrfs scrub start /ponto` | **Varre** o FS verificando checksums (montado) |
| `btrfs scrub status /ponto` | Andamento/resultado |
| `btrfs filesystem df /ponto` | Espaço por tipo (data/metadata/system) |
| `btrfs filesystem usage /ponto` | Visão **detalhada** de uso (**`df` engana em Btrfs**) |

### 14.2 FAT/VFAT (pendrives, partição EFI)

```bash
sudo fsck.vfat -n /dev/sdb1     # = dosfsck -n  → só verifica
sudo fsck.vfat -a /dev/sdb1     # repara automaticamente
sudo fsck.vfat -r /dev/sdb1     # repara interativamente
sudo fsck.vfat -v /dev/sdb1     # verbose
```

FAT **não tem journal**; quedas de energia/remoção sem "ejetar" são causas comuns de corrupção.

### 14.3 Identificar o tipo do FS antes de escolher a ferramenta

```bash
lsblk -f                 # árvore de dispositivos + FSTYPE + UUID + ponto de montagem
blkid /dev/sdb1          # tipo, UUID, label
findmnt /dados           # FS montado, tipo e opções
file -s /dev/sdb1        # lê a assinatura do dispositivo (precisa de root)
```

Escolha da ferramenta:

| Tipo do FS | Verificar/reparar |
|---|---|
| ext2/3/4 | `fsck` / `e2fsck` |
| XFS | `xfs_repair` |
| Btrfs | `btrfs check` / `btrfs scrub` |
| FAT/VFAT | `fsck.vfat` / `dosfsck` |

## 15. Sinais de problema no disco

Corrupção de FS pode ser **sintoma** de um problema **físico** (disco falhando, cabo ruim, controladora). Reparar o FS sem tratar a causa é "enxugar gelo".

### 15.1 Logs do kernel

```bash
dmesg -T | grep -Ei 'error|ext4|xfs|i/o|sd[a-z]|ata[0-9]'
journalctl -k -p err               # mensagens de erro do kernel (systemd)
```

Mensagens que **acendem o alerta**:

```
EXT4-fs error (device sdb1): ext4_find_entry: reading directory #2 offset 0
blk_update_request: I/O error, dev sdb, sector 123456
XFS (sdb1): Metadata corruption detected at ...
EXT4-fs (sdb1): Remounting filesystem read-only
```

### 15.2 SMART (saúde do disco)

```bash
sudo smartctl -H /dev/sda       # resumo: PASSED / FAILED
sudo smartctl -a /dev/sda       # atributos (Reallocated_Sector_Ct, Current_Pending_Sector...)
sudo smartctl -t short /dev/sda # teste curto
```
(pacote `smartmontools`.) Atributos como **setores realocados** e **pendentes** crescentes indicam disco em fim de vida.

### 15.3 `badblocks`

Procura **blocos defeituosos** no dispositivo.

```bash
sudo badblocks -sv /dev/sdb1          # leitura (não destrutivo), com progresso
sudo badblocks -nsv /dev/sdb1         # teste de leitura/escrita NÃO destrutivo (lento)
sudo badblocks -wsv /dev/sdb1         # ⚠ teste DESTRUTIVO (apaga dados!)
```

Em ext, o mais prático é `e2fsck -c` (executa `badblocks` e **registra** os blocos ruins no inode de *bad blocks*).

## 16. Fluxos de trabalho práticos

### 16.1 Fluxo A — Verificar uma partição de dados (ext4)

```bash
# 1) Identifique o FS e onde está montado
lsblk -f
findmnt /dados

# 2) Pare quem está usando e desmonte
sudo fuser -vm /dados          # quem usa? (ou: sudo lsof +f -- /dados)
sudo systemctl stop servico    # pare serviços dependentes
sudo umount /dados

# 3) Avalie sem alterar
sudo e2fsck -fn /dev/sdb1

# 4) Repare (preferindo o modo seguro primeiro)
sudo e2fsck -fp /dev/sdb1      # se parar pedindo intervenção manual →
sudo e2fsck -f  /dev/sdb1      # modo interativo

# 5) Reverifique até sair com código 0 e monte novamente
sudo e2fsck -f /dev/sdb1; echo $?
sudo mount /dados

# 6) Revise lost+found
sudo ls -l /dados/lost+found
```

### 16.2 Fluxo B — Superbloco corrompido (ext4)

```bash
sudo dumpe2fs /dev/sdb1 | grep -i 'backup superblock'    # tenta listar
# se falhar:
sudo mke2fs -n /dev/sdb1                                 # ⚠ dry-run! Só mostra posições

sudo e2fsck -b 32768 /dev/sdb1                           # usa o backup
sudo mount /dev/sdb1 /dados
```

### 16.3 Fluxo C — Sistema raiz com problema

1. Reinicie e acesse o **GRUB** (tecla `e` na entrada), adicione `fsck.mode=force fsck.repair=yes` (ou `systemd.unit=rescue.target`) → `Ctrl+X`.
2. **Ou** boot em **live USB** → `lsblk -f` → `e2fsck -f /dev/sda2`.
3. Se `/` caiu em **somente leitura** em produção: planeje janela de manutenção, **backup**, e verificação com `/` desmontado.

### 16.4 Fluxo D — Disco cheio / sem espaço

```
"No space left on device"
        │
        ├─► df -h        → blocos cheios?  ──► du -ahx / | sort -rh | head ; limpar
        │                                     └─► df ≫ du ? → lsof +L1 (apagados abertos)
        │
        └─► df -i        → inodes cheios?  ──► localizar diretório com milhões de arquivos ; limpar
```

### 16.5 Fluxo E — XFS

```bash
sudo umount /dados
sudo xfs_repair -n /dev/sdb1                 # analisa
sudo xfs_repair /dev/sdb1                    # repara
# log sujo e não monta? → (último recurso, pode perder dados recentes)
sudo xfs_repair -L /dev/sdb1
```

## 17. Cenários reais de servidor

### Cenário 1 — "Não consigo criar arquivos, mas há 60% livre"

```console
$ df -h /var
/dev/sda3   20G   8G   11G  42% /var
$ df -i /var
/dev/sda3  1310720 1310720 0 100% /var
```
**Diagnóstico:** inodes esgotados. **Ação:** achar o diretório com milhões de arquivos (`find`/loop de contagem) e limpar. Longo prazo: recriar com `mke2fs -i`/`-N` menor razão bytes/inode, ou migrar para XFS.

### Cenário 2 — "Apaguei o log gigante e o disco continua 100%"

**Diagnóstico:** arquivo apagado mas aberto. **Ação:** `lsof +L1` → reiniciar o serviço ou `truncate -s 0 /proc/PID/fd/N`. **Prevenção:** `logrotate` com `copytruncate`/sinal de reabertura.

### Cenário 3 — Após queda de energia, o servidor para no *emergency mode*

**Diagnóstico:** `fsck -p` do boot achou problema que não pode corrigir sozinho. **Ação:** com a senha de root: `journalctl -xb`, identificar o dispositivo, `e2fsck -f /dev/...` (responder às perguntas ou `-y` após avaliar com `-n`), `exit`/`reboot`.

### Cenário 4 — Aplicação reclama "Read-only file system"

**Diagnóstico:** `dmesg` mostra erro e "Remounting filesystem read-only" (`errors=remount-ro`). **Ação:** investigar o **hardware** (SMART, cabos), fazer **backup** do que for possível, desmontar e rodar `e2fsck`. Reiniciar só para "limpar" sem tratar a causa tende a reincidir.

### Cenário 5 — `mount` falha: "bad superblock"

**Ação:** `dumpe2fs`/`mke2fs -n` para achar backups → `e2fsck -b <bloco>` → remontar.

### Cenário 6 — Volume XFS não monta após falha

**Ação:** `dmesg` → tentar `mount` (reexecuta o log) → `xfs_repair -n` → `xfs_repair` → só em último caso `xfs_repair -L`.

### Cenário 7 — Quero que o servidor **nunca** pare para checar disco no boot

**Ação:** `tune2fs -c 0 -i 0 /dev/sdX` (desativa checagem periódica). **Contrapartida:** erros silenciosos podem se acumular; combine com **monitoramento**, SMART e janelas de manutenção para `fsck` programado.

## 18. Tabelas-resumo e "cola" para a prova

### 18.1 Qual ferramenta para qual tarefa?

| Tarefa | Comando |
|---|---|
| Espaço livre por FS | `df -h` |
| Tipo de FS na saída | `df -T` |
| **Inodes** livres | `df -i` |
| Espaço usado por diretório | `du -sh dir` |
| Ordenar maiores diretórios | `du -h --max-depth=1 \| sort -h` |
| Verificar ext2/3/4 | `e2fsck -f` / `fsck -t ext4` |
| Só simular (sem alterar) | `e2fsck -n` |
| Reparo automático seguro | `e2fsck -p` |
| Responder "sim" a tudo | `e2fsck -y` |
| Forçar mesmo se *clean* | `e2fsck -f` |
| Usar superbloco de backup | `e2fsck -b N` |
| Ver onde estão os backups | `dumpe2fs \| grep -i superblock` / `mke2fs -n` |
| Ver/alterar parâmetros ext | `tune2fs -l` / `tune2fs ...` |
| Controlar checagem periódica | `tune2fs -c` (montagens) / `-i` (tempo) |
| Comportamento em erro | `tune2fs -e continue\|remount-ro\|panic` |
| Reserva do root | `tune2fs -m` / `-r` |
| Dump do superbloco/grupos | `dumpe2fs` (`-h` só o cabeçalho) |
| Depurar ext interativamente | `debugfs` |
| Verificar/reparar XFS | `xfs_repair` (`-n` simula, `-L` zera log) |
| Depurar XFS | `xfs_db` |
| Desfragmentar XFS | `xfs_fsr` |
| Geometria XFS | `xfs_info` |

### 18.2 Comparativo dos modos do `e2fsck`

| Opção | Pergunta? | Altera o FS? | Quando usar |
|---|---|---|---|
| `-n` | Não (responde "não") | ❌ | **Diagnóstico** |
| `-p` | Não (corrige só o seguro) | ✅ (limitado) | **Boot automático** |
| `-y` | Não (responde "sim") | ✅ | Reparos amplos (ciente do risco) |
| (nenhuma) | **Sim, interativo** | ✅ | Controle caso a caso |
| `-f` | — | — | **Força** a checagem (combina com os acima) |

### 18.3 `df` x `du`

| | `df` | `du` |
|---|---|---|
| Foco | Sistema de arquivos | Arquivos/diretórios |
| Fonte | Superbloco (`statfs`) | Percorre a árvore |
| Enxerga arquivo apagado mas aberto? | ✅ (espaço ocupado) | ❌ |
| Inclui metadados/journal/reserva? | ✅ | ❌ |
| Mostra inodes? | ✅ (`-i`) | ❌ |
| Funciona sem montar? | ❌ | ❌ (precisa acessar os arquivos) |

### 18.4 Valores do 6º campo do `/etc/fstab`

| Valor | Quando |
|---|---|
| `0` | Não checar (XFS, Btrfs, tmpfs, NFS, swap...) |
| `1` | Apenas `/` |
| `2` | Demais FS que devem ser checados |

## 19. Pegadinhas clássicas de prova

1. **`fsck` em FS montado** → **nunca** em leitura/escrita. Desmontar primeiro.
2. **`-p` vs `-a` vs `-y` vs `-n`**: `-p`/`-a` = automático "seguro"; `-y` = sim a tudo; `-n` = não altera nada. São **exclusivos** entre si.
3. **`-f`**: sem ele, FS *clean* é **pulado** ("clean, X/Y files, ...").
4. **`mke2fs -n`** = dry-run (**não** formata). Sem `-n` → **formata e apaga tudo**.
5. **`df` ≠ `du`**: a diferença costuma vir de **arquivos apagados e ainda abertos**, reserva de 5% e metadados.
6. **"No space left on device" com espaço livre** → **inodes** (`df -i`).
7. **Inode não guarda o nome**; o nome está na entrada de diretório.
8. **`lost+found`**: arquivos recuperados com nome = **número do inode** (`#12345`).
9. **XFS não usa `fsck`**: usa `xfs_repair` (desmontado). `fsck.xfs` **não faz nada**.
10. **`xfs_repair -L`** = **zera o log**, último recurso; antes, tente **montar/desmontar** para reproduzir o log.
11. **Backups do superbloco**: **8193** (bloco de 1 KB) e **32768** (bloco de 4 KB).
12. **`fstab` 6º campo**: `1` só para `/`, `2` para os demais, `0` = sem checagem.
13. **`tune2fs -c 0 -i 0`** desativa as checagens periódicas.
14. **`tune2fs -l`** ≈ **`dumpe2fs -h`** (listam o superbloco). Só o `tune2fs` altera.
15. **`debugfs`** abre em **somente leitura** por padrão; `-w` para escrita.
16. **`du -s`** = total; **`du -h`** = legível; **`du -x`** = não cruza FS; **`du -d N`** = profundidade.
17. **`df -h` (1024) vs `df -H` (1000)**.
18. **Journaling ≠ ausência de `fsck`**: reduz a necessidade e acelera a recuperação após queda; não corrige defeito físico/lógico profundo.
19. **ext2 não tem journal**; ext3 = ext2 + journal; ext4 = evolução (extents etc.).
20. **Número de inodes em ext é fixo** na criação (XFS/Btrfs são dinâmicos).
