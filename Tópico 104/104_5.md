## 2. Conceitos fundamentais: usuário, grupo e "outros"

No Linux, **todo arquivo e diretório possui exatamente**:

- **Um dono (owner / user)** — normalmente quem criou o arquivo.
- **Um grupo (group)** — um grupo de usuários associado ao arquivo.
- **Permissões separadas para três classes de "quem":**

| Classe | Letra no `chmod` | Quem é |
|---|---|---|
| **Usuário (dono)** | `u` | O dono do arquivo |
| **Grupo** | `g` | Membros do grupo associado ao arquivo |
| **Outros** | `o` | Qualquer outro usuário do sistema |
| **Todos** | `a` | `u` + `g` + `o` (atalho do `chmod`) |

### A regra de ouro da avaliação

O Linux verifica **na ordem**: primeiro, "você é o dono?"; se não, "você pertence ao grupo?"; se não, aplica "outros". **Apenas uma classe é aplicada** — a primeira que casar. Isso gera uma pegadinha clássica:

> Se o dono tem `---` (nenhuma permissão) e "outros" tem `rwx`, **o dono não consegue acessar o arquivo**, mesmo que todos os outros consigam. O sistema não "soma" classes: ele para na primeira que se aplica.

### O usuário root

O `root` (UID 0) **ignora as permissões de leitura e escrita** na prática (pode ler/escrever praticamente tudo). Para **execução**, porém, mesmo o root precisa que **pelo menos um bit `x`** esteja ligado para executar um arquivo comum.

## 3. Lendo a saída do `ls -l`

```bash
$ ls -l
-rwxr-xr--  1  maria  devs  4096  out 22 10:30  script.sh
drwxr-x---  2  maria  devs  4096  out 22 10:31  projeto
lrwxrwxrwx  1  maria  devs     9  out 22 10:32  atalho -> script.sh
```

Dissecando a primeira linha, campo por campo:

```
-rwxr-xr--  1  maria  devs  4096  out 22 10:30  script.sh
│└┬┘└┬┘└┬┘  │    │      │     │         │          │
│ │  │  │   │    │      │     │         │          └─ nome do arquivo
│ │  │  │   │    │      │     │         └─ data/hora da última modificação
│ │  │  │   │    │      │     └─ tamanho em bytes
│ │  │  │   │    │      └─ grupo
│ │  │  │   │    └─ dono
│ │  │  │   └─ número de links físicos (hard links)
│ │  │  └─ permissões de "outros"  (r--)
│ │  └─ permissões do grupo        (r-x)
│ └─ permissões do dono            (rwx)
└─ tipo do arquivo
```

### O primeiro caractere: tipo de arquivo

| Caractere | Tipo |
|---|---|
| `-` | Arquivo regular |
| `d` | Diretório |
| `l` | Link simbólico |
| `c` | Dispositivo de caractere (ex.: `/dev/tty`) |
| `b` | Dispositivo de bloco (ex.: `/dev/sda`) |
| `p` | Pipe nomeado (FIFO) |
| `s` | Socket |

### Os 9 caracteres seguintes

São **três grupos de três** (`rwx` `rwx` `rwx`) para dono, grupo e outros. Cada posição pode ser a letra (permissão concedida) ou `-` (permissão negada).

### Como os bits especiais aparecem no `ls -l`

Os bits especiais "pegam emprestada" a posição do `x`:

| Aparência | Significado |
|---|---|
| `rws` na posição do dono | **SUID** ativo **e** `x` ativo |
| `rwS` na posição do dono | **SUID** ativo, mas **sem** `x` (situação geralmente inútil/errada) |
| `rws` na posição do grupo | **SGID** ativo **e** `x` ativo |
| `rwS` na posição do grupo | **SGID** ativo, mas **sem** `x` |
| `rwt` na posição de outros | **Sticky bit** ativo **e** `x` ativo |
| `rwT` na posição de outros | **Sticky bit** ativo, mas **sem** `x` |

**Memorize:** letra **minúscula** (`s`, `t`) = bit especial + execução. Letra **MAIÚSCULA** (`S`, `T`) = bit especial **sem** execução.

## 4. O significado de r, w, x em arquivos e diretórios

Este é um dos pontos mais importantes: **as mesmas letras significam coisas diferentes** para arquivos e diretórios.

### Em arquivos regulares

| Bit | Valor | Significado |
|---|---|---|
| `r` (read) | 4 | Ler o conteúdo do arquivo (`cat`, `less`, `cp` como origem...) |
| `w` (write) | 2 | Modificar o conteúdo do arquivo (editar, truncar, `>>`) |
| `x` (execute) | 1 | Executar o arquivo como programa ou script |

> **Atenção:** para executar um **script** (`./script.sh` direto), é preciso `x`. Mas para rodar `bash script.sh`, basta `r`, pois quem é executado é o `bash`, e o script é apenas lido.

### Em diretórios

Aqui está a maior fonte de confusão. Lembre que um diretório é, no fundo, **uma lista de nomes de arquivos associados a inodes**.

| Bit | Valor | Significado em diretório |
|---|---|---|
| `r` | 4 | **Listar** os nomes dentro do diretório (`ls`) |
| `w` | 2 | **Criar, remover e renomear** entradas (arquivos) dentro do diretório — *requer também `x`* |
| `x` | 1 | **Atravessar/acessar** o diretório (`cd`, acessar arquivos dentro dele pelo caminho) |

### Combinações importantes em diretórios

| Permissão | Efeito prático |
|---|---|
| `r-x` | Pode listar e entrar; pode ler arquivos (se eles permitirem). **Não** cria nem apaga. |
| `--x` | Pode entrar e acessar arquivos **se souber o nome exato**, mas **não consegue listar** (`ls` falha). |
| `r--` | Consegue ver os nomes (`ls` mostra nomes), mas **não** consegue acessar metadados nem entrar (`cd` falha). Mostra erros de "Permission denied" nos detalhes. |
| `rwx` | Controle total sobre as entradas do diretório. |
| `-wx` | Pode criar/remover/entrar, mas não listar. Situação incomum. |
| `rw-` | **Inútil na prática**: sem `x`, o `w` não funciona. |

### A pegadinha mais famosa: apagar arquivo não depende da permissão do arquivo

> **Para remover um arquivo, o que importa é a permissão `w` (+`x`) do DIRETÓRIO que o contém — e não a permissão do arquivo em si.**

Exemplo: um arquivo com `---------` (nenhuma permissão) pode ser apagado por quem tem `w` e `x` no diretório pai. O `rm` pode pedir confirmação ("remove write-protected file?"), mas, confirmando, apaga.

Da mesma forma, **ter `w` no arquivo não permite apagá-lo** se você não tiver `w` no diretório. Você consegue editar o conteúdo, mas não removê-lo.

### Exemplo prático

```bash
$ mkdir cofre
$ echo "segredo" > cofre/dados.txt
$ chmod 711 cofre          # dono: rwx | grupo: --x | outros: --x

# Como outro usuário:
$ ls cofre                 # FALHA: ls: cannot open directory 'cofre': Permission denied
$ cat cofre/dados.txt      # FUNCIONA (se o arquivo permitir leitura e você souber o nome)
```

Isso mostra a diferença entre `r` (listar) e `x` (atravessar) em diretórios.

## 5. Alterando permissões: `chmod`

O `chmod` (*change mode*) muda as permissões. Só pode ser usado pelo **dono do arquivo** ou pelo **root**.

Há **dois modos** de especificar permissões: **simbólico** e **octal (numérico)**.

### 5.1. Modo simbólico

**Sintaxe:**

```
chmod [quem][operador][permissões] arquivo
```

| Componente | Valores |
|---|---|
| **quem** | `u` (dono), `g` (grupo), `o` (outros), `a` (todos) |
| **operador** | `+` (adiciona), `-` (remove), `=` (define exatamente) |
| **permissões** | `r`, `w`, `x`, `s` (SUID/SGID), `t` (sticky), `X` (x condicional) |

**Exemplos:**

```bash
chmod u+x script.sh        # adiciona execução ao dono
chmod g-w arquivo          # remove escrita do grupo
chmod o=r arquivo          # outros terão APENAS leitura (sobrescreve o que havia)
chmod a+r arquivo          # todos ganham leitura
chmod ug+rw arquivo        # dono e grupo ganham leitura e escrita
chmod u=rwx,g=rx,o= arq    # define cada classe separadamente (outros sem nada)
chmod +x script.sh         # sem "quem": aplica a todos, MAS respeitando o umask (veja seção 7)
```

> **Detalhe sutil:** `chmod +x` (sem especificar quem) usa o `umask` para decidir a quem aplicar. Já `chmod a+x` aplica sempre a todos. Na prática, com umask comum (022), ambos resultam em `x` para todos, mas a diferença existe e pode cair em prova.

**Copiando permissões de uma classe para outra:**

```bash
chmod g=u arquivo    # o grupo recebe as mesmas permissões que o dono tem
chmod o=g arquivo    # outros recebem as permissões do grupo
```

**O `X` maiúsculo (execução condicional):**

```bash
chmod -R a+rX diretorio/
```

O `X` concede execução **somente** se o item for um **diretório** ou se **já tiver execução para alguém**. Isso é ótimo para aplicar permissões recursivamente sem tornar arquivos comuns executáveis.

### 5.2. Modo octal (numérico)

Cada permissão tem um valor, e **somamos** os valores de cada classe:

| Permissão | Valor |
|---|---|
| `r` | **4** |
| `w` | **2** |
| `x` | **1** |
| nenhuma | 0 |

Cada classe vira **um dígito** (0 a 7). Três dígitos = dono, grupo, outros.

| Octal | Binário | Simbólico | Cálculo |
|---|---|---|---|
| 0 | 000 | `---` | 0 |
| 1 | 001 | `--x` | 1 |
| 2 | 010 | `-w-` | 2 |
| 3 | 011 | `-wx` | 2+1 |
| 4 | 100 | `r--` | 4 |
| 5 | 101 | `r-x` | 4+1 |
| 6 | 110 | `rw-` | 4+2 |
| 7 | 111 | `rwx` | 4+2+1 |

**Exemplos de conversão:**

```
rwxr-xr--  →  (4+2+1)(4+0+1)(4+0+0)  →  754
rw-r--r--  →  (4+2+0)(4+0+0)(4+0+0)  →  644
rwx------  →  (4+2+1)(0)(0)          →  700
rwxrwxrwx  →  777
rw-rw----  →  660
```

**Uso:**

```bash
chmod 755 script.sh     # rwxr-xr-x  (padrão comum de programas)
chmod 644 arquivo.txt   # rw-r--r--  (padrão comum de arquivos)
chmod 600 chave_privada # rw-------  (exigido pelo SSH para chaves privadas)
chmod 700 ~/.ssh        # rwx------
```

### 5.3. Octal com 4 dígitos (permissões especiais)

Quando há bits especiais, adiciona-se **um dígito à esquerda**:

| Valor | Bit especial |
|---|---|
| **4** | SUID |
| **2** | SGID |
| **1** | Sticky Bit |

Soma-se como nas permissões normais:

```bash
chmod 4755 programa     # SUID + rwxr-xr-x    → -rwsr-xr-x
chmod 2755 diretorio    # SGID + rwxr-xr-x    → drwxr-sr-x
chmod 1777 /tmp         # Sticky + rwxrwxrwx  → drwxrwxrwt
chmod 6755 arquivo      # SUID + SGID         → -rwsr-sr-x
chmod 7777 arquivo      # SUID + SGID + Sticky + rwxrwxrwx
```

> **Se você usar apenas 3 dígitos** no modo octal em um arquivo que já tem bits especiais, o `chmod` pode **limpar** esses bits em certos casos (especialmente em diretórios no GNU coreutils, o comportamento é de preservar SUID/SGID com 3 dígitos; para removê-los é preciso usar `0755` ou `chmod g-s`). Para não depender de detalhes, **prefira ser explícito**: use 4 dígitos ou o modo simbólico (`u+s`, `g+s`, `o+t`).

### 5.4. Opções importantes do `chmod`

| Opção | Efeito |
|---|---|
| `-R` | Recursivo: aplica a diretórios e todo o conteúdo |
| `-v` | *verbose*: mostra o que mudou para cada arquivo |
| `-c` | Como `-v`, mas só mostra os arquivos que **realmente mudaram** |
| `-f` | Silencia a maioria das mensagens de erro |
| `--reference=ARQ` | Copia as permissões de outro arquivo (`chmod --reference=modelo.txt alvo.txt`) |

### 5.5. Cuidado com `chmod -R`

```bash
chmod -R 755 /var/www     # torna TODOS os arquivos executáveis, inclusive .txt, .html, imagens...
```

Isso raramente é o desejado. Solução mais correta:

```bash
find /var/www -type d -exec chmod 755 {} \;   # diretórios: 755
find /var/www -type f -exec chmod 644 {} \;   # arquivos:   644
```

Ou, usando o `X`:

```bash
chmod -R u=rwX,go=rX /var/www
```

## 6. Alterando dono e grupo: `chown` e `chgrp`

### 6.1. `chown` (*change owner*)

**Apenas o root pode mudar o dono de um arquivo** (um usuário comum **não pode** "doar" seus arquivos a outro — isso evita burlar cotas de disco e responsabilidade).

**Sintaxe geral:**

```bash
chown [opções] NOVO_DONO[:NOVO_GRUPO] arquivo...
```

| Comando | Efeito |
|---|---|
| `chown joao arquivo` | Muda **apenas o dono** para `joao` |
| `chown joao:devs arquivo` | Muda **dono** para `joao` **e grupo** para `devs` |
| `chown :devs arquivo` | Muda **apenas o grupo** para `devs` |
| `chown joao: arquivo` | Muda o dono para `joao` e o grupo para o **grupo de login** de `joao` |
| `chown -R joao:devs pasta/` | Recursivo |
| `chown --reference=modelo alvo` | Copia dono e grupo de outro arquivo |

> **Sobre o separador:** a forma moderna e recomendada é `usuario:grupo` (dois pontos). A forma antiga `usuario.grupo` (ponto) ainda pode funcionar, mas é **ambígua** quando o nome do usuário contém ponto. Na prova, considere os dois pontos como o padrão.

**Opções úteis:**

| Opção | Efeito |
|---|---|
| `-R` | Recursivo |
| `-v` / `-c` | Verbose / mostra só mudanças |
| `-h` / `--no-dereference` | Altera o **próprio link simbólico**, em vez do arquivo apontado |
| `-L` / `-H` / `-P` | Controlam como links simbólicos são seguidos em operações recursivas |
| `--from=DONO:GRUPO` | Só altera se o dono/grupo **atual** forem os informados |

```bash
chown --from=joao maria arquivo.txt   # só muda para maria SE o dono atual for joao
```

### 6.2. `chgrp` (*change group*)

Muda **somente o grupo** do arquivo.

```bash
chgrp devs arquivo           # muda o grupo para devs
chgrp -R devs projeto/       # recursivo
```

**Quem pode usar?**
- O **root**: pode mudar para qualquer grupo.
- O **dono do arquivo**: pode mudar o grupo **somente para um grupo do qual ele mesmo é membro**.

### 6.3. Efeito de `chown` nos bits especiais

Quando um arquivo muda de dono (ou grupo) por um usuário comum, o kernel **remove automaticamente os bits SUID e SGID** do arquivo por segurança. Isso evita que se transfira um programa privilegiado para outro dono mantendo o poder.

## 7. Permissão padrão para novos arquivos: `umask`

### 7.1. O que é

O `umask` é uma **máscara** que define **quais permissões serão REMOVIDAS** dos arquivos e diretórios quando eles são criados. Ele não "dá" permissões — ele **subtrai** de um valor-base.

### 7.2. Os valores-base

| Tipo criado | Permissão-base máxima |
|---|---|
| **Arquivo** regular | `666` (rw-rw-rw-) — **nunca nasce com `x`** |
| **Diretório** | `777` (rwxrwxrwx) |

> **Por que arquivos não nascem com `x`?** Por segurança: um arquivo recém-criado não deve ser executável automaticamente. Isso é uma decisão dos programas/kernel, e o `umask` simplesmente remove bits desse máximo.

### 7.3. O cálculo (a forma correta)

A forma **correta** é por **operação de bits**: `permissão final = base AND (NOT umask)`. Ou seja, **remove-se os bits do umask**.

**Exemplo com umask `022`:**

```
Arquivos:    666 → remove 022 → 644  (rw-r--r--)
Diretórios:  777 → remove 022 → 755  (rwxr-xr-x)
```

**Exemplo com umask `077`:**

```
Arquivos:    666 → 600  (rw-------)
Diretórios:  777 → 700  (rwx------)
```

**Exemplo com umask `002`:**

```
Arquivos:    666 → 664  (rw-rw-r--)
Diretórios:  777 → 775  (rwxrwxr-x)
```

**Exemplo com umask `027`:**

```
Arquivos:    666 → 640  (rw-r-----)
Diretórios:  777 → 750  (rwxr-x---)
```

### 7.4. ⚠️ A pegadinha da "subtração"

Subtrair decimalmente nem sempre funciona. Veja um caso em que **subtrair** e **remover bits** dão resultados diferentes:

```
umask 025, criando arquivo (base 666):

Subtração ingênua:     666 - 025 = 641   ← ERRADO

Remoção de bits:
  666 = 110 110 110
  025 = 000 010 101
  
  Dono:   110 sem 000 = 110 = 6
  Grupo:  110 sem 010 = 100 = 4
  Outros: 110 sem 101 = 010 = 2   ← remove r(4) e x(1); como x não existia, só r sai → fica w(2)

Resultado correto: 642
```

Veja que a subtração ingênua dá `641`, mas o correto é `642`, porque o "1" (execução) do umask tenta remover um `x` que **nem existia** no arquivo. **Regra prática:** olhe bit a bit; remova apenas o que existe.

### 7.5. Usando o comando

```bash
$ umask            # mostra o umask atual em octal
0022

$ umask -S         # mostra em formato simbólico (o que é PERMITIDO)
u=rwx,g=rx,o=rx

$ umask 077        # define para a sessão atual do shell
$ touch teste
$ ls -l teste
-rw------- 1 maria maria 0 out 22 10:40 teste
```

> **Observe:** `umask -S` mostra o que fica **permitido**, e não o que é mascarado. É o "inverso" do valor octal.

### 7.6. Tornando o umask permanente

O `umask` definido na linha de comando vale **só para aquela sessão**. Para tornar permanente:

| Local | Alcance |
|---|---|
| `~/.bashrc` ou `~/.profile` | Apenas para o usuário |
| `/etc/profile` | Para todos os usuários (shells de login) |
| `/etc/bash.bashrc` (Debian/Ubuntu) ou `/etc/bashrc` (RHEL/CentOS) | Para shells interativos de todos |
| `/etc/login.defs` (parâmetro `UMASK`) | Padrão para novos usuários/logins |
| PAM (`pam_umask`) | Configuração via módulo PAM |

### 7.7. Valores típicos

| umask | Contexto |
|---|---|
| `022` | Padrão tradicional para `root` e muitas distribuições |
| `002` | Comum em distros que usam **grupo privado por usuário** (ex.: Debian/Ubuntu para usuários comuns, RHEL/Fedora) |
| `077` | Ambientes que exigem máxima privacidade |
| `027` | Grupo lê; outros nada |

## 8. Permissões especiais: SUID, SGID e Sticky Bit

São **três bits extras** que modificam o comportamento normal. São cobradíssimos na prova.

### 8.1. SUID (Set User ID) — valor 4

**Em arquivos executáveis:** o programa é executado com os privilégios do **DONO do arquivo**, e não do usuário que o executou.

**Exemplo clássico: `/usr/bin/passwd`**

```bash
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 59976 ... /usr/bin/passwd
```

Um usuário comum precisa alterar `/etc/shadow` (que só o root escreve) ao trocar a senha. Como o `passwd` tem SUID e pertence ao root, ele roda **como root** durante a execução, permitindo a alteração controlada.

**Como aplicar/remover:**

```bash
chmod u+s programa     # simbólico
chmod 4755 programa    # octal
chmod u-s programa     # remove
```

**Aparência:**
- `-rwsr-xr-x` → SUID + execução
- `-rwSr--r--` → SUID **sem** execução (provavelmente configuração incorreta)

**Em diretórios:** o SUID **é ignorado** no Linux.

**Em scripts:** o SUID **não funciona** em scripts interpretados (shell scripts) na maioria dos sistemas Linux modernos, por razões de segurança. Funciona em binários compilados.

> **Segurança:** programas SUID de root são alvos clássicos de ataque. Audite periodicamente (veja o `find` na seção 9).

### 8.2. SGID (Set Group ID) — valor 2

O SGID tem **dois comportamentos distintos**, dependendo de onde é aplicado.

**a) Em arquivos executáveis:** o programa roda com os privilégios do **GRUPO do arquivo**.

```bash
$ ls -l /usr/bin/locate      # (em algumas distros)
-rwxr-sr-x 1 root slocate ... /usr/bin/locate
```

**b) Em diretórios (uso mais cobrado):** **arquivos e subdiretórios criados dentro herdam o GRUPO do diretório**, em vez do grupo primário de quem os criou. Subdiretórios criados também herdam o próprio bit SGID.

```bash
$ mkdir /srv/projeto
$ chgrp devs /srv/projeto
$ chmod 2775 /srv/projeto
$ ls -ld /srv/projeto
drwxrwsr-x 2 root devs 4096 ... /srv/projeto

# Maria (grupo primário: maria) cria um arquivo lá dentro:
$ touch /srv/projeto/relatorio.txt
$ ls -l /srv/projeto/relatorio.txt
-rw-rw-r-- 1 maria devs 0 ... relatorio.txt     ← grupo = devs (herdado!)
```

**Para que serve?** É a base de **diretórios colaborativos**: todos os membros do grupo `devs` criam arquivos que o grupo `devs` pode editar, sem precisar rodar `chgrp` manualmente.

**Aplicar/remover:**

```bash
chmod g+s diretorio     # simbólico
chmod 2775 diretorio    # octal
chmod g-s diretorio     # remove
```

> **Observação:** o SGID em diretório **faz o grupo ser herdado**, mas **não altera as permissões** dos novos arquivos (quem controla isso é o `umask`). Se o `umask` for 022, os novos arquivos **não** terão escrita para o grupo, e a colaboração falha. Por isso é comum combinar SGID com `umask 002`.

### 8.3. Sticky Bit — valor 1

**Em diretórios:** dentro do diretório, **cada usuário só pode apagar ou renomear os arquivos de que é dono** (ou, se for o dono do diretório, ou o root), **mesmo que tenha `w` no diretório**.

**Exemplo clássico: `/tmp`**

```bash
$ ls -ld /tmp
drwxrwxrwt 15 root root 4096 ... /tmp
```

Todos têm `rwx` em `/tmp` (por isso qualquer um cria arquivos lá). Sem o sticky bit, **qualquer um poderia apagar os arquivos dos outros** (pois `w` no diretório permite remover entradas). Com o sticky bit (`t`), só o dono do arquivo (ou do diretório, ou o root) pode remover/renomear.

**Aplicar/remover:**

```bash
chmod +t diretorio      # simbólico (equivale a o+t)
chmod o+t diretorio
chmod 1777 diretorio    # octal
chmod -t diretorio      # remove
```

**Aparência:**
- `drwxrwxrwt` → sticky + execução para outros
- `drwxrwxrwT` → sticky **sem** execução para outros

**Em arquivos:** nos sistemas Linux modernos o sticky bit em arquivos é **ignorado**. (Historicamente, em Unix antigos, mantinha o programa em memória/swap após execução — daí o nome "sticky".)

### 8.4. Resumo comparativo

| Bit | Octal | Simbólico | Em **arquivos** | Em **diretórios** | Aparece como |
|---|---|---|---|---|---|
| **SUID** | 4 | `u+s` | Executa com privilégios do **dono** | Ignorado | `s`/`S` no dono |
| **SGID** | 2 | `g+s` | Executa com privilégios do **grupo** | Novos itens **herdam o grupo** do diretório | `s`/`S` no grupo |
| **Sticky** | 1 | `o+t` | Ignorado (Linux moderno) | Só o dono do item (ou do dir, ou root) **apaga/renomeia** | `t`/`T` em outros |

### 8.5. Montando o dígito especial (4 dígitos)

```
   ┌── dígito especial (SUID=4, SGID=2, Sticky=1)
   │ ┌── dono
   │ │ ┌── grupo
   │ │ │ ┌── outros
   4 7 5 5   →  SUID + rwxr-xr-x

   Exemplos:
   4755 → -rwsr-xr-x    (SUID)
   2755 → -rwxr-sr-x    (SGID)
   1755 → -rwxr-xr-t    (Sticky)
   6755 → -rwsr-sr-x    (SUID + SGID)
   3755 → -rwxr-sr-t    (SGID + Sticky)
   7755 → -rwsr-sr-t    (os três)
```

## 9. Localizando arquivos por permissão com `find`

O `find` tem opções específicas para filtrar por **permissão**, **dono** e **grupo**. É a ferramenta de auditoria.

### 9.1. `-perm` — as três formas

| Forma | Significado |
|---|---|
| `-perm 644` | Permissões **exatamente** `644` |
| `-perm -644` | **Todos** os bits informados estão ligados (pode ter **mais** bits) |
| `-perm /644` | **Pelo menos um** dos bits informados está ligado (`-perm +644` é a forma antiga, obsoleta) |

**Memorize com o mnemônico:**
- *sem prefixo* = **exato**
- `-` (traço) = **todos** os bits listados
- `/` (barra) = **qualquer um** dos bits listados

### 9.2. Exemplos comentados

```bash
# Arquivos com SUID ligado (qualquer outro bit pode estar presente):
find / -perm -4000 -type f 2>/dev/null
find / -perm -u=s -type f 2>/dev/null        # equivalente simbólico

# Arquivos com SGID:
find / -perm -2000 -type f 2>/dev/null
find / -perm -g=s -type f 2>/dev/null

# SUID OU SGID (qualquer um dos dois):
find / -perm /6000 -type f 2>/dev/null

# Arquivos com escrita para "outros" (risco de segurança):
find /var -perm -o=w -type f 2>/dev/null
find /var -perm -002 -type f 2>/dev/null

# Arquivos EXATAMENTE 777:
find /home -perm 777

# Diretórios com sticky bit:
find / -perm -1000 -type d 2>/dev/null
```

### 9.3. Filtros por dono e grupo

```bash
find / -user joao                 # arquivos cujo dono é joao
find / -group devs                # arquivos cujo grupo é devs
find / -nouser                    # arquivos cujo UID não corresponde a nenhum usuário (órfãos)
find / -nogroup                   # arquivos cujo GID não corresponde a nenhum grupo
find / -uid 1001                  # por UID numérico
find / -gid 1001                  # por GID numérico
```

> **Cenário real:** ao remover um usuário com `userdel` (sem apagar seus arquivos), os arquivos dele ficam "órfãos", mostrando um **número** no lugar do dono. O `find / -nouser` encontra todos eles.

### 9.4. Combinando com ações

```bash
# Remover escrita de "outros" em todos os arquivos regulares sob /srv:
find /srv -type f -perm -o=w -exec chmod o-w {} \;

# Listar com detalhes os SUID encontrados:
find / -perm -4000 -type f -exec ls -l {} \; 2>/dev/null
```

## 10. Comandos auxiliares: `stat`, `id`, `groups`, `newgrp`, `su`/`sudo`

### 10.1. `stat` — detalhes completos de um arquivo

```bash
$ stat script.sh
  File: script.sh
  Size: 120        Blocks: 8          IO Block: 4096   regular file
Device: 801h/2049d  Inode: 131090     Links: 1
Access: (0754/-rwxr-xr--)  Uid: ( 1000/   maria)   Gid: ( 1000/   devs)
Access: 2026-10-22 10:30:00.000000000 -0300
Modify: 2026-10-22 10:30:00.000000000 -0300
Change: 2026-10-22 10:35:12.000000000 -0300
```

**O valor de ouro:** a linha `Access: (0754/-rwxr-xr--)` mostra o **octal e o simbólico lado a lado**, com UID/GID numéricos e nomes.

Formatação customizada:

```bash
stat -c '%a %U:%G %n' arquivo     # ex.: 754 maria:devs arquivo
stat -c '%A' arquivo              # ex.: -rwxr-xr--
```

| Formato | Significado |
|---|---|
| `%a` | Permissões em octal |
| `%A` | Permissões em formato legível |
| `%U` / `%G` | Nome do dono / grupo |
| `%u` / `%g` | UID / GID numérico |
| `%n` | Nome do arquivo |

### 10.2. `id` e `groups`

```bash
$ id
uid=1000(maria) gid=1000(maria) groups=1000(maria),27(sudo),1001(devs)

$ groups
maria sudo devs

$ id joao      # consulta outro usuário
```

- **`uid`**: ID do usuário · **`gid`**: grupo **primário** · **`groups`**: todos os grupos **secundários** (suplementares).

### 10.3. Grupo primário vs. secundário

- **Primário:** é o grupo atribuído por padrão a **novos arquivos** que o usuário criar (a menos que o diretório tenha SGID).
- **Secundários:** grupos adicionais que **concedem acesso** a recursos, mas não são o grupo padrão de novos arquivos.

### 10.4. `newgrp` — trocar o grupo primário temporariamente

```bash
$ newgrp devs        # abre um novo shell com 'devs' como grupo primário
$ touch teste        # o grupo do arquivo será devs
$ exit               # volta ao shell anterior
```

> **Atenção:** o `newgrp` inicia um **novo shell**. Use `exit` para voltar.

### 10.5. Adicionar usuário a um grupo (contexto)

```bash
usermod -aG devs maria     # -a (append) é ESSENCIAL; sem ele, substitui todos os grupos secundários!
gpasswd -a maria devs
```

> O novo grupo só vale em **novas sessões** de login. A sessão atual não é atualizada (a menos que use `newgrp`, `su - maria` etc.).

## 11. Como o kernel decide se você pode acessar um arquivo

Fluxo de decisão para um processo que tenta acessar um arquivo:

```
1. O processo é do root (UID 0)?
      └─ SIM → acesso concedido para r/w (para x, precisa de ao menos um bit x ligado)
      └─ NÃO → vá para o passo 2

2. O UID efetivo do processo == dono do arquivo?
      └─ SIM → aplica SOMENTE as permissões do DONO (e para aqui)
      └─ NÃO → vá para o passo 3

3. O GID do processo (primário ou algum secundário) == grupo do arquivo?
      └─ SIM → aplica SOMENTE as permissões do GRUPO (e para aqui)
      └─ NÃO → vá para o passo 4

4. Aplica as permissões de "OUTROS".
```

**Consequência importante:** o acesso é decidido pela **primeira classe que corresponde**. Exemplos:

| Arquivo | Quem acessa | Resultado |
|---|---|---|
| `----rwxrwx` dono=maria | maria | **Negado** (aplica-se a classe "dono": `---`) |
| `-rw-r-----` dono=maria, grupo=devs | joao (membro de devs) | **Lê** (classe grupo: `r--`), **não** escreve |
| `-rw-r--rw-` dono=maria, grupo=devs | joao (membro de devs) | **Só lê** (classe grupo: `r--`); a escrita de "outros" **não** se aplica a ele |

### E o caminho (path)?

Para acessar `/home/maria/docs/arq.txt`, você precisa de **`x` em cada diretório do caminho** (`/`, `/home`, `/home/maria`, `/home/maria/docs`) **e** da permissão adequada no arquivo. Se **qualquer diretório intermediário** negar `x`, o acesso falha, não importa quão permissivo seja o arquivo.

## 12. Cenários práticos completos

### Cenário 1 — Script que "não executa"

```bash
$ ./backup.sh
bash: ./backup.sh: Permission denied

$ ls -l backup.sh
-rw-r--r-- 1 maria maria 210 ... backup.sh
```

**Diagnóstico:** falta o `x`. **Correção:**

```bash
chmod u+x backup.sh
./backup.sh
```

*Alternativa sem alterar permissões:* `bash backup.sh` (só precisa de `r`).

### Cenário 2 — Pasta compartilhada para a equipe

**Objetivo:** `/srv/equipe` onde todos do grupo `devs` criam e editam arquivos uns dos outros, e ninguém de fora acessa.

```bash
mkdir /srv/equipe
chgrp devs /srv/equipe
chmod 2770 /srv/equipe       # SGID + rwx para dono e grupo; nada para outros
```

Para que os arquivos criados também sejam **editáveis pelo grupo**, os usuários devem ter `umask 002` (ou `007`):

```bash
umask 002
touch /srv/equipe/ata.txt
ls -l /srv/equipe/ata.txt
# -rw-rw-r-- 1 maria devs ...   ← grupo devs (SGID) com escrita (umask 002)
```

### Cenário 3 — Diretório público de "caixa de entrada"

**Objetivo:** `/srv/inbox` onde todos podem depositar arquivos, mas ninguém apaga os dos outros.

```bash
mkdir /srv/inbox
chmod 1777 /srv/inbox        # sticky + rwxrwxrwx
```

### Cenário 4 — Chave SSH rejeitada

```
Permissions 0644 for '/home/maria/.ssh/id_rsa' are too open.
It is required that your private key files are NOT accessible by others.
```

**Correção:**

```bash
chmod 600 ~/.ssh/id_rsa
chmod 700 ~/.ssh
```

### Cenário 5 — Auditoria de segurança (SUID inesperado)

```bash
find / -perm -4000 -type f 2>/dev/null | sort > /root/suid_atual.txt
diff /root/suid_baseline.txt /root/suid_atual.txt
```

Qualquer SUID novo, não presente na linha de base, merece investigação.

### Cenário 6 — Transferindo a posse de um projeto

```bash
chown -R joao:devs /srv/projeto
find /srv/projeto -type d -exec chmod 2775 {} \;     # SGID nos diretórios
find /srv/projeto -type f -exec chmod 664 {} \;
```

### Cenário 7 — Leitura sem listagem (diretório "cego")

```bash
chmod 711 /srv/publico
# Outros podem acessar /srv/publico/relatorio.pdf (sabendo o nome)
# mas NÃO conseguem fazer 'ls /srv/publico'
```

### Cenário 8 — Usuário removido e arquivos órfãos

```bash
$ ls -l /srv/dados
-rw-r--r-- 1 1005 1005 100 ... antigo.txt     ← UID/GID numéricos: usuário não existe mais

$ find / -nouser -o -nogroup 2>/dev/null
$ chown -R novo_dono:novo_grupo /srv/dados
```

## 13. Armadilhas e pegadinhas de prova

1. **Diretório sem `x` torna o `w` inútil.** `rw-` em diretório não permite criar nem apagar nada.
2. **Apagar arquivo depende do diretório**, não do arquivo.
3. **Só a primeira classe correspondente vale** (dono → grupo → outros). O dono sem permissão fica barrado mesmo que "outros" tenha `rwx`.
4. **Root ignora `r` e `w`**, mas **não executa** arquivo sem nenhum bit `x`.
5. **`umask` não é subtração decimal** — remova bits (veja caso `025`).
6. **Arquivos nunca nascem com `x`** (base 666), diretórios nascem com base 777.
7. **`s`/`t` minúsculos** = bit especial + `x`; **`S`/`T` maiúsculos** = bit especial **sem** `x`.
8. **SUID em diretório é ignorado**; SGID em diretório = **herança de grupo**; sticky em diretório = **proteção contra remoção alheia**.
9. **SUID não funciona em shell scripts** no Linux moderno.
10. **`chown` só pelo root**; `chgrp` pelo dono apenas para grupos dos quais ele participa.
11. **`chmod -R 777`** é quase sempre errado. Prefira `find -type d/-type f` ou `X`.
12. **`usermod -G` (sem `-a`)** substitui todos os grupos secundários.
13. **`find -perm`:** sem prefixo = exato; `-` = todos os bits; `/` = qualquer um.
14. **`chmod +x` sem "quem"** respeita o `umask`; `a+x` não.
15. **`umask -S`** mostra o que é **permitido**, não o que é mascarado.
16. Mudanças de grupo (`usermod -aG`) só valem após **novo login**.
17. **Links simbólicos:** o `chmod` em um link simbólico altera as permissões do **alvo**; as permissões do link em si (`lrwxrwxrwx`) são irrelevantes.
18. **Copiar (`cp`) cria um arquivo novo** → dono é quem copiou, permissões seguem o `umask` (a menos que use `cp -p` ou `cp -a` para preservar).
19. **Mover (`mv`) dentro do mesmo sistema de arquivos** preserva dono/permissões (só renomeia a entrada); entre sistemas de arquivos diferentes, comporta-se como copiar + apagar.

## 14. Tabelas de revisão rápida

### 14.1. Octal ↔ Simbólico (mais comuns)

| Octal | Simbólico | Uso típico |
|---|---|---|
| `777` | `rwxrwxrwx` | Acesso total (evitar!) |
| `755` | `rwxr-xr-x` | Programas e diretórios públicos |
| `750` | `rwxr-x---` | Diretório do grupo, fechado a outros |
| `700` | `rwx------` | Privado do dono (ex.: `~/.ssh`) |
| `666` | `rw-rw-rw-` | Escrita livre (evitar) |
| `664` | `rw-rw-r--` | Arquivos colaborativos de grupo |
| `644` | `rw-r--r--` | Arquivos de dados comuns |
| `640` | `rw-r-----` | Arquivo legível pelo grupo |
| `600` | `rw-------` | Privado do dono (ex.: chaves privadas) |
| `400` | `r--------` | Somente leitura pelo dono |
| `4755` | `rwsr-xr-x` | Binário SUID (ex.: `passwd`) |
| `2775` | `rwxrwsr-x` | Diretório colaborativo (SGID) |
| `1777` | `rwxrwxrwt` | Diretório público com sticky (ex.: `/tmp`) |

### 14.2. Tabela do `umask`

| umask | Arquivo | Diretório |
|---|---|---|
| `000` | 666 | 777 |
| `002` | 664 | 775 |
| `022` | 644 | 755 |
| `027` | 640 | 750 |
| `077` | 600 | 700 |
| `007` | 660 | 770 |

### 14.3. Comandos do tópico

| Comando | Função |
|---|---|
| `chmod` | Altera permissões (simbólico ou octal) |
| `chown` | Altera dono (e opcionalmente grupo) — root |
| `chgrp` | Altera grupo |
| `umask` | Exibe/define a máscara de criação |
| `ls -l` / `ls -ld` | Exibe permissões (`-d` para o próprio diretório) |
| `stat` | Detalhes completos (octal + símbolos + UID/GID) |
| `find -perm/-user/-group` | Busca por permissão/dono/grupo |
| `id` / `groups` | Mostra identidade e grupos |
| `newgrp` | Muda o grupo primário temporariamente |

### 14.4. Quem pode fazer o quê

| Ação | Quem pode |
|---|---|
| `chmod` em um arquivo | Dono ou root |
| `chown` (mudar dono) | Somente root |
| `chgrp` (mudar grupo) | Root; ou dono, para grupos de que participa |
| Remover arquivo | Quem tem `w`+`x` no **diretório** (+ regra do sticky bit, se houver) |
