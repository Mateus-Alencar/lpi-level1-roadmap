## Tópico 102.3: Controle de bibliotecas compartilhadas

#### Objetivos
- Identificar bibliotecas compartilhadas
- Identificar onde geralmente essas bibliotecas se localizam no sistema
- Carregar as bibliotecas compartilhadas

#### Arquivos, termos e comandos importantes
- `ldd`
- `ldconfig`
- `ldconfig -p`
- `/etc/ld.so.conf`
- `/etc/ld.so.conf.d/`
- `/etc/ld.so.cache`
- `LD_LIBRARY_PATH`

> [!NOTE]
> O **compilador** transforma o código-fonte em código de máquina, que é armazenado nos chamados **arquivos-objeto** (`.o`). Esses arquivos-objeto ainda não são um programa executável — é o **vinculador** (*linker*) quem os une às bibliotecas para gerar o executável final.

---

### Bibliotecas estáticas

Uma cópia do código da biblioteca é incorporada ao programa e se torna parte dele. Portanto, o programa não tem dependências na biblioteca em tempo de execução, pois já contém o código da biblioteca.

- Extensão típica: `.a` (archive)
- **Vantagem:** o binário é autossuficiente, não depende de bibliotecas externas presentes no sistema.
- **Desvantagens:**
  - Arquivo executável final maior (o código é duplicado em cada programa que a utiliza);
  - Correções de bugs ou atualizações de segurança na biblioteca exigem **recompilação** de todos os programas que a utilizam.

### Bibliotecas compartilhadas (dinâmicas)

O vinculador simplesmente cuida para que o programa faça referência às bibliotecas corretamente, mas **não copia** nenhum código da biblioteca para o arquivo do programa. Assim, a biblioteca compartilhada deve estar disponível em **tempo de execução** para satisfazer as dependências do programa.

- Extensão típica: `.so` (*Shared Object*)
- **Vantagens:**
  - Economiza espaço em disco e memória RAM, pois vários programas podem usar a mesma cópia da biblioteca carregada;
  - Uma atualização/correção na biblioteca beneficia automaticamente todos os programas que a utilizam, sem necessidade de recompilação.
- **Desvantagem:** o programa depende da presença da biblioteca correta no sistema em tempo de execução (o famoso problema de *dependency hell*).

> Bibliotecas compartilhadas ajudam a economizar recursos do sistema.

---

### Convenções de nomenclatura

```
lib(nome).so.(versão_maior).(versão_menor).(liberação)
```

- **Prefixo `lib`:** quase todas as bibliotecas no Linux começam obrigatoriamente com o prefixo `lib` (ex.: `libm.so`, `libssl.so`).
- **Sufixo `.so`:** abreviação de *Shared Object*, equivalente ao `.dll` no Windows.
- **Números de versão:** adicionados após o `.so` para controle de compatibilidade de interface binária (ABI).

**Exemplo prático**

Se for instalada a versão 1.2.3 de uma biblioteca fictícia chamada `graphics`, o diretório `/usr/lib` ou `/usr/local/lib` conterá a seguinte estrutura de arquivo real + links simbólicos:

| Arquivo | Tipo | Aponta para |
|---|---|---|
| `libgraphics.so.1.2.3` | Arquivo real | — |
| `libgraphics.so.1` | **Soname** (link simbólico) | `libgraphics.so.1.2.3` |
| `libgraphics.so` | *Linker Name* (link simbólico) | `libgraphics.so.1` |

- O **arquivo real** contém o código compilado da versão exata.
- O **soname** (*Shared Object Name*) é usado pelo sistema em tempo de execução para localizar a biblioteca; representa a versão maior, garantindo compatibilidade de ABI.
- O **linker name** é usado apenas em tempo de **compilação/link** (ex.: com a flag `-lgraphics`), geralmente apontando para a versão mais recente disponível.

> Se os desenvolvedores lançarem uma correção de bug na versão 1.2.4 (que não quebra compatibilidade), o sistema atualizará o link do soname (`libgraphics.so.1`) para apontar para o novo arquivo `libgraphics.so.1.2.4`. Todos os programas que dependem de `libgraphics.so.1` passarão a usar a versão corrigida automaticamente, sem necessidade de recompilação.

> [!NOTE]
> O conceito de bibliotecas compartilhadas não é exclusivo do Linux. No Windows, por exemplo, elas são chamadas de **DLL** (*Dynamic-Link Library*), bibliotecas de vínculo dinâmico.

---

### Onde as bibliotecas ficam localizadas

Os diretórios padrão onde o sistema procura por bibliotecas compartilhadas são:

- `/lib` e `/lib64` — bibliotecas essenciais para o boot e para os binários em `/bin` e `/sbin`;
- `/usr/lib` e `/usr/lib64` — bibliotecas de programas instalados no sistema;
- `/usr/local/lib` — bibliotecas instaladas manualmente pelo administrador, fora do gerenciador de pacotes.

> [!NOTE]
> Em distribuições modernas é comum `/lib` ser apenas um link simbólico para `/usr/lib` (unificação de diretórios, o chamado *UsrMerge*).

---

### `ldd` — verificando dependências de um binário

O comando `ldd` mostra quais bibliotecas compartilhadas um executável (ou outra biblioteca) precisa, e se o vinculador dinâmico está conseguindo resolvê-las.

```bash
$ ldd /bin/ls
	linux-vdso.so.1 (0x00007ffd...)
	libselinux.so.1 => /lib/x86_64-linux-gnu/libselinux.so.1 (0x00007f...)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
	/lib64/ld-linux-x86-64.so.2 (0x00007f...)
```

- Se uma biblioteca aparece como `=> not found`, significa que o programa **não vai executar**, pois uma dependência está ausente ou não está no caminho de busca do vinculador.

> [!WARNING]
> Por segurança, **nunca** execute `ldd` em binários de origem não confiável: em algumas circunstâncias o `ldd` pode acabar executando o próprio binário para resolver as dependências. Prefira `objdump -p arquivo | grep NEEDED` nesses casos.

---

### O vinculador dinâmico e o cache (`ld.so.cache`)

Quando um programa é executado, quem carrega as bibliotecas compartilhadas na memória é o **vinculador/carregador dinâmico** (`ld.so` ou `ld-linux.so`), e não o kernel diretamente.

Para não precisar varrer o disco inteiro toda vez que um programa é iniciado, o sistema mantém um **cache binário** em `/etc/ld.so.cache`, que é gerado a partir de:

1. Os diretórios padrão de bibliotecas (`/lib`, `/usr/lib`, etc.);
2. Os diretórios listados no arquivo `/etc/ld.so.conf` (geralmente via `include /etc/ld.so.conf.d/*.conf`);
3. Os arquivos `.conf` dentro de `/etc/ld.so.conf.d/`, cada um normalmente contendo um caminho por linha, usado por pacotes de terceiros para registrar seus próprios diretórios de bibliotecas.

### `ldconfig` — reconstruindo o cache

Sempre que uma nova biblioteca é instalada em um dos diretórios configurados (ou um novo diretório é adicionado ao `/etc/ld.so.conf.d/`), é necessário **reconstruir o cache** para que o sistema passe a "enxergá-la":

```bash
# Reconstrói o cache em /etc/ld.so.cache a partir de /etc/ld.so.conf
$ sudo ldconfig

# Lista todas as bibliotecas (compartilhadas) atualmente conhecidas pelo cache
$ ldconfig -p
	libzstd.so.1 (libc6,x86-64) => /lib/x86_64-linux-gnu/libzstd.so.1
	libz.so.1 (libc6,x86-64) => /lib/x86_64-linux-gnu/libz.so.1
	...

# Modo "verbose", mostra também os links simbólicos sendo (re)criados
$ sudo ldconfig -v
```
> [!NOTE]  
> `ldconfig` relê `/etc/ld.so.conf` e todos os arquivos em `/etc/ld.so.conf.d/*.conf` reconstruindo o cache binário `/etc/ld.so.cache`   

- Também é `ldconfig` quem cria/atualiza automaticamente os links simbólicos de *soname* (ex.: `libgraphics.so.1 → libgraphics.so.1.2.4`) para as bibliotecas encontradas nos diretórios configurados.
- Muitos gerenciadores de pacotes (como `apt` e `dnf`) chamam `ldconfig` automaticamente após instalar um pacote que contenha bibliotecas.

---

### `LD_LIBRARY_PATH` — sobrepondo o caminho de busca

`LD_LIBRARY_PATH` é uma **variável de ambiente** que permite indicar diretórios adicionais (com prioridade sobre o cache padrão) onde o vinculador dinâmico deve procurar bibliotecas, **sem** precisar alterar `/etc/ld.so.conf` nem rodar `ldconfig`.

```bash
$ export LD_LIBRARY_PATH=/opt/minhaslibs:$LD_LIBRARY_PATH
$ ./meu_programa
```

- Muito usada para **testar** uma versão específica/experimental de uma biblioteca, ou para rodar programas que dependem de bibliotecas instaladas fora dos diretórios padrão (ex.: softwares proprietários), sem afetar o restante do sistema.
- É válida apenas para a sessão/processo atual (variável de ambiente), diferente de `/etc/ld.so.conf`, que é uma configuração **persistente** e global do sistema.

> [!NOTE]
> Ordem de precedência (resumida) na busca por bibliotecas em tempo de execução:
> 1. `RPATH`/`RUNPATH` embutido no binário (se existir);
> 2. `LD_LIBRARY_PATH`;
> 3. Cache do `ldconfig` (`/etc/ld.so.cache`);
> 4. Diretórios padrão (`/lib`, `/usr/lib`).

### Resumo rápido para revisão

| Comando/Arquivo | Função |
|---|---|
| `ldd <binário>` | Lista as bibliotecas compartilhadas exigidas por um binário e mostra se foram resolvidas |
| `ldconfig` | Reconstrói o cache `/etc/ld.so.cache` e atualiza os links de soname |
| `ldconfig -p` | Lista as bibliotecas atualmente conhecidas pelo cache |
| `/etc/ld.so.conf` | Arquivo principal com diretórios adicionais de bibliotecas |
| `/etc/ld.so.conf.d/` | Diretório com arquivos `.conf` extras (um por pacote/aplicação) (arquivo de configurações modulares) |
| `LD_LIBRARY_PATH` | Variável de ambiente para adicionar diretórios de busca temporários, com prioridade alta |
