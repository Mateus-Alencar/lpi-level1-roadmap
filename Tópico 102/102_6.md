## 1. Máquinas Virtuais vs. Contêineres

### 1.1 Máquina Virtual (VM)
Uma **máquina virtual** é a emulação completa de um computador físico, feita por software. Ela roda seu **próprio kernel** e seu próprio sistema operacional completo, isolado do hospedeiro.

- Controlada por um **hypervisor** (também chamado VMM — Virtual Machine Monitor), que pode ser:
  - **Tipo 1 (bare-metal)**: roda diretamente sobre o hardware. Ex.: **KVM**, Xen, VMware ESXi, Hyper-V.
  - **Tipo 2 (hospedado)**: roda sobre um SO já instalado. Ex.: VirtualBox, VMware Workstation, QEMU (modo emulado puro).
- No Linux, a combinação mais cobrada na LPI é **KVM + QEMU**:
  - **KVM** (Kernel-based Virtual Machine) — módulo do kernel que transforma o Linux em hypervisor tipo 1, usando extensões de virtualização de hardware da CPU (Intel VT-x / AMD-V).
  - **QEMU** — emulador de hardware/máquina que trabalha junto com o KVM para fornecer dispositivos virtuais (disco, rede, vídeo etc.).
- Overhead maior que contêineres (cada VM carrega um kernel e SO inteiros), mas isolamento mais forte.

### 1.2 Contêiner (Contêiner Linux)
Um **contêiner** isola processos em nível de sistema operacional, **compartilhando o mesmo kernel** do hospedeiro. É mais leve e rápido de iniciar que uma VM.

- Baseado em recursos do kernel Linux:
  - **Namespaces** — isolam o que o processo "enxerga" (PID, rede, montagens, usuários, hostname/UTS, IPC).
  - **cgroups (control groups)** — limitam e contabilizam o uso de recursos (CPU, memória, I/O).
- Ferramentas/tecnologias associadas:
  - **LXC (Linux Containers)** — contêiner de sistema, mais próximo de uma VM leve, roda um SO/init completo dentro do contêiner.
  - **systemd-nspawn** — ferramenta do systemd para criar contêineres leves.

### 1.3 Contêiner de Aplicação
Diferente do contêiner de sistema (LXC), o **contêiner de aplicação** empacota **uma única aplicação e suas dependências**, não um SO inteiro.

- Exemplo clássico: **Docker** (e o runtime **containerd**, padrão OCI).
- Ideia central: "constrói uma vez, roda em qualquer lugar" — a imagem contém tudo que a aplicação precisa (bibliotecas, binários), mas ainda usa o kernel do hospedeiro.
- Diferença-chave para a prova:

| Característica | Contêiner de Sistema (LXC) | Contêiner de Aplicação (Docker) |
|---|---|---|
| O que roda dentro | Um SO completo (init, múltiplos processos) | Um processo/aplicação principal |
| Analogia | VM leve | Processo empacotado |
| Ciclo de vida | Longo, como um servidor | Curto, efêmero, recriável |

### 1.4 Resumo comparativo VM x Contêiner

| | Máquina Virtual | Contêiner |
|---|---|---|
| Kernel | Próprio | Compartilhado com o host |
| Isolamento | Forte (hardware virtualizado) | Mais fraco (isolamento via namespaces/cgroups) |
| Peso/tempo de boot | Pesado, minutos | Leve, segundos |
| Tecnologia típica no Linux | KVM/QEMU, Xen | LXC, Docker |

## 2. Elementos comuns em VMs numa nuvem IaaS

Em um provedor **IaaS** (Infrastructure as a Service — ex.: AWS, Azure, GCP, OpenStack), uma VM não existe isolada: ela é composta por recursos combináveis:

- **Instância computacional (compute instance)**: a própria VM — CPU, memória RAM e um "tamanho"/tipo (flavor) pré-definido pelo provedor.
- **Armazenamento em bloco (block storage)**: disco virtual anexado à instância (ex.: AWS EBS). É independente do ciclo de vida da instância — pode ser desanexado e reanexado a outra VM, e frequentemente é a base para criar **imagens/snapshots**.
- **Rede (networking)**: inclui endereços IP (privados/públicos), interfaces de rede virtuais, grupos de segurança/firewall e redes virtuais isoladas (VPCs) que conectam as instâncias.

A ideia central para a prova: essas três peças são **desacopladas** — você pode trocar o armazenamento, mudar a rede ou redimensionar a instância de forma relativamente independente.

## 3. Propriedades exclusivas que precisam mudar ao clonar/usar como modelo

Quando uma VM (ou imagem) é usada como **modelo (template)** para criar clones, alguns identificadores **precisam ser regenerados**, pois deveriam ser únicos por máquina:

- **Chaves SSH do host (Host SSH keys)**: cada sistema Linux gera, na primeira inicialização, um par de chaves do servidor SSH (`/etc/ssh/ssh_host_*_key`). Se um clone mantiver as mesmas chaves do modelo, todos os clones terão a **mesma identidade SSH**, o que é um problema de segurança (risco de MITM, avisos de "chave alterada" ao conectar) e de identificação única do host.
- **ID de máquina do D-Bus / systemd (`/etc/machine-id`)**: identificador único de 32 caracteres hexadecimais gerado por máquina, usado pelo **D-Bus** e pelo **systemd** para identificar o sistema (logs, journald, DHCP client, etc.). Deve ser único por instalação — se copiado entre clones, quebra a identificação individual de cada sistema.
- Outros itens comumente lembrados junto (mesmo raciocínio de "unicidade"):
  - **Hostname**
  - **Endereço MAC** das interfaces de rede virtuais
  - **UUID do sistema de arquivos** (em alguns cenários de clonagem de disco)

> Ferramentas como `virt-sysprep` (no mundo KVM/libvirt) automatizam essa "despersonalização" de um template antes da clonagem, e o `cloud-init` cuida disso automaticamente na primeira inicialização de instâncias de nuvem (veja seção 5).

Para regenerar manualmente:
```bash
# Machine ID (D-Bus/systemd)
rm /etc/machine-id
systemd-machine-id-setup

# Chaves SSH do host
rm /etc/ssh/ssh_host_*
ssh-keygen -A
```
#### `ssh-keygen`  
Usado para gerar, gerenciar e converter chaves de autenticação SSH  
**Exemplos de uso**  
```bash
# Gerar par de chaves ed25519 com comentário
ssh-keygen -t ed25519 -C "usuario@servidor"

# Gerar RSA de 4096 bits, sem senha, em arquivo específico
ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_deploy -N ""

# Ver o fingerprint de uma chave
ssh-keygen -l -f ~/.ssh/id_ed25519.pub

# Trocar a passphrase de uma chave existente
ssh-keygen -p -f ~/.ssh/id_rsa

# Regenerar todas as chaves de host do sistema (ex.: após clonar uma VM)
ssh-keygen -A

# Remover um host desatualizado do known_hosts
ssh-keygen -R servidor.exemplo.com
```   
**Arquivos**  
- Chaves do usuário: `~/.ssh/id_rsa`  
- Chaves do host (servidor SSH): `/etc/ssh/ssh_host_*_key`

## 4. Imagens de sistema

Uma **imagem de sistema** é um arquivo (ou conjunto de arquivos) que contém um sistema operacional (ou parte dele) pronto para ser instanciado, sem precisar passar por uma instalação tradicional.

- **VMs**: imagens de disco completas, em formatos como:
  - **qcow2** (QEMU Copy-On-Write) — formato nativo do QEMU/KVM, suporta snapshots e alocação dinâmica de espaço.
  - **raw** — imagem de disco "crua", sem otimizações.
  - **OVA/OVF** — formato de empacotamento/portabilidade entre hypervisores.
- **Instâncias de nuvem**: imagens específicas do provedor, frequentemente derivadas de uma instância já configurada e "limpa" (sem as propriedades únicas vistas na seção 3). Ex.: AMI na AWS.
- **Contêineres**: imagens em camadas (layers), como as do **Docker/OCI**, definidas por um `Dockerfile` — cada instrução cria uma camada, e as camadas são reaproveitadas entre imagens para economizar espaço e tempo de build.

Ideia central para a prova: em todos os três casos, a imagem é o **modelo reutilizável** a partir do qual novas instâncias/contêineres são criados rapidamente, evitando reinstalar o SO do zero.

## 5. Extensões do Linux para integração com virtualização

Essas extensões (frequentemente chamadas de **guest additions/tools** ou **drivers de convidado**) são instaladas **dentro da VM convidada (guest)** para melhorar desempenho e integração com o hospedeiro/hypervisor:

- **Drivers de convidado (guest drivers)**: dispositivos "para-virtualizados" que substituem emulação genérica lenta por drivers otimizados cientes de que estão rodando numa VM. Exemplo central: **VirtIO** — família de drivers para-virtualizados (disco, rede, etc.) usada com KVM/QEMU, muito mais rápida que a emulação de hardware real.
- Pacotes de integração específicos por hypervisor:
  - **open-vm-tools** — integração com VMware (mouse, resolução de tela, compartilhamento de área de transferência, sincronização de tempo).
  - **VirtualBox Guest Additions** — equivalente para VirtualBox.
  - **hyperv daemons (hv_*)** — integração com Hyper-V.
  - **Xen guest tools / drivers PV** — integração com Xen.

Essas ferramentas tipicamente fornecem: melhor desempenho de I/O, resolução de tela dinâmica, compartilhamento de arquivos/clipboard entre host e guest, sincronização de relógio e desligamento/reinicialização controlados pelo host.

## 6. Noções de cloud-init

**cloud-init** é o utilitário padrão da indústria para **inicialização e personalização automática** de instâncias de nuvem (e VMs em geral) no primeiro boot.

- Lê **metadados** fornecidos pela plataforma de nuvem (via um serviço de metadados HTTP, um CD-ROM virtual, etc.) e/ou um arquivo de **user-data** fornecido pelo usuário ao criar a instância.
- Tarefas típicas realizadas automaticamente no primeiro boot:
  - Definir o **hostname**.
  - Configurar a **rede** (IP, DNS).
  - Redimensionar o sistema de arquivos para ocupar todo o disco.
  - Criar usuários e **injetar chaves SSH públicas** (autorizando acesso sem senha).
  - Regenerar as **chaves SSH do host** e o **machine-id** (resolvendo o problema da seção 3).
  - Instalar pacotes e executar scripts arbitrários definidos pelo usuário.
- Formato do **user-data**: geralmente **YAML** (começa com `#cloud-config`), mas também aceita scripts shell puros (`#!`).
- Arquivos de configuração relevantes: `/etc/cloud/cloud.cfg` (config principal) e `/etc/cloud/cloud.cfg.d/` (overrides).
- Módulos rodam em estágios (ex.: `init`, `config`, `final`), cada um em um momento diferente do boot.

Exemplo simples de `user-data`:
```yaml
#cloud-config
hostname: servidor01
users:
  - name: admin
    ssh-authorized-keys:
      - ssh-rsa AAAA...
    sudo: ALL=(ALL) NOPASSWD:ALL
packages:
  - nginx
runcmd:
  - systemctl enable nginx
```

## 7. Glossário rápido (termos cobrados pela LPI)

| Termo | Definição curta |
|---|---|
| **Máquina Virtual** | Emulação de um computador completo, com kernel/SO próprios, gerenciada por um hypervisor |
| **Contêiner Linux** | Isolamento de processos em nível de SO, compartilhando o kernel do host (ex.: LXC) |
| **Contêiner de Aplicação** | Empacota uma aplicação e suas dependências, não um SO inteiro (ex.: Docker) |
| **Drivers de convidado** | Drivers para-virtualizados instalados no guest para melhor desempenho/integração (ex.: VirtIO) |
| **Chaves SSH do host** | Par de chaves únicas por servidor SSH; devem ser regeneradas em clones |
| **ID de máquina D-Bus** (`/etc/machine-id`) | Identificador único do sistema, usado por D-Bus/systemd; deve ser único por instalação |

---

## Resumo  

1. Diferença entre **contêiner de sistema (LXC)** e **contêiner de aplicação (Docker)**.
2. Saber que **VMs têm kernel próprio**; **contêineres compartilham** o kernel do host.
3. Reconhecer **KVM** (parte do kernel) e **QEMU** (emulação) como a dupla central de virtualização no Linux.
4. Saber **o que precisa mudar** ao clonar um sistema: chaves SSH do host e `/etc/machine-id` (e citar hostname/MAC como itens relacionados).
5. Entender que **cloud-init** resolve automaticamente essa "despersonalização" e injeta configuração (rede, hostname, chaves SSH) no primeiro boot.
6. Associar **armazenamento em bloco** como recurso desacoplado da instância em um ambiente IaaS.
7. Reconhecer termos como **VirtIO** e **open-vm-tools** como exemplos de drivers/extensões de integração guest-host.
