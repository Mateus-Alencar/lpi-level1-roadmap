## 1. Conceitos

### 1.1 Kernel

**Kernel**: núcleo central do sistema operacional Linux. Atua como ponte entre o hardware e os softwares/aplicativos.

Principais funções:
- Gerenciamento de processos
- Gerenciamento da memória RAM
- Gerenciamento de dispositivos de hardware
- Gerenciamento do sistema de arquivos
- Comunicação entre hardware e software

> [!NOTE]
> O kernel executa em **kernel space**, enquanto os programas do usuário executam em **user space**. Essa separação evita que um erro em um programa comum derrube o sistema inteiro.

### 1.2 Drivers e módulos

**Driver**: software que permite ao kernel controlar um dispositivo de hardware. No Linux, um driver pode estar:

| Forma | Descrição |
|---|---|
| **Built-in** | Compilado **dentro** do kernel; sempre presente, não pode ser descarregado |
| **Módulo** (`.ko`) | Componente **carregável** em tempo de execução, sem recompilar nem reiniciar |

**Módulo**: arquivo `.ko` (*kernel object*) que adiciona funcionalidades ao kernel dinamicamente. Ficam em `/lib/modules/<versão-do-kernel>/`.

Vantagens dos módulos:
- Economia de memória (só carrega o que é usado)
- Inicialização mais rápida
- Suporte dinâmico a novos dispositivos
- Kernel base menor

> [!NOTE]
> A maioria dos drivers no Linux é módulo. Eles só entram na memória quando o hardware correspondente é detectado/plugado.

**Parâmetros de módulo:** muitos módulos aceitam opções (ex.: `modprobe snd_hda_intel power_save=0`). Para listar os parâmetros disponíveis, use `modinfo -p <módulo>`; os valores atuais ficam em `/sys/module/<módulo>/parameters/`.

**Daemons (serviços)**: programas executados em segundo plano (*background*) que realizam tarefas automatizadas ou fornecem funcionalidades sem intervenção do usuário. Não possuem interface gráfica e, geralmente, iniciam automaticamente com o sistema (ex.: `udevd`, `sshd`).

### 1.3 Dispositivos coldplug × hotplug

| Tipo | Definição | Exemplos |
|---|---|---|
| **Coldplug** | Só podem ser conectados/removidos com o equipamento **desligado**; são enumerados no boot | CPU, RAM, placa-mãe, placas PCI internas comuns |
| **Hotplug** | Podem ser conectados/removidos com o sistema **ligado** e são detectados dinamicamente pelo kernel + udev | USB, SATA com hot-swap, PCMCIA, Thunderbolt, PCIe hotplug (servidores) |

> [!NOTE]
> É o **udev** quem trata os eventos de hotplug, criando/removendo os arquivos correspondentes em `/dev` em tempo real.

> [!TIP] Não confundir
> No boot, o udev também faz a chamada **"coldplug"** (*replay*): reenvia eventos dos dispositivos que **já estavam presentes** para que seus módulos sejam carregados e seus nós criados. É o que o comando `udevadm trigger` faz manualmente.

### 1.4 BIOS × UEFI

| BIOS | UEFI |
|---|---|
| Mais antigo, 16 bits | Mais moderno, 32/64 bits |
| Usa **MBR** (4 partições primárias; discos até ~2 TB) | Usa **GPT** (discos enormes, até 128 partições por padrão) |
| Lê o código de boot nos primeiros setores do disco | Lê arquivos `.efi` da **ESP** (*EFI System Partition*, normalmente FAT32) |
| Sem Secure Boot | Suporta **Secure Boot** |
| Interface em modo texto | Interface gráfica, suporte a mouse |

- Configurações de hardware embutido (placa de som, rede, portas seriais/USB, modo SATA) geralmente são habilitadas/desabilitadas pelo **BIOS/UEFI Setup** (teclas `Del`, `F2`, `F10`, `F12`... conforme o fabricante).
- No Linux também é possível consultar/alterar parâmetros em tempo de execução via `/sys` ou ferramentas específicas (ex.: `setpci` para registradores PCI).
- Muitas placas UEFI têm um modo de compatibilidade (**CSM/Legacy**) que permite boot em modo BIOS.

> [!TIP] Como saber se o sistema iniciou em UEFI ou BIOS
> ```bash
> ls /sys/firmware/efi      # existe → boot UEFI; não existe → BIOS/legacy
> ```

> [!NOTE]
> **MBR** e **GPT** são formatos de particionamento: a estrutura gravada no disco que diz onde cada partição começa e termina. Para gerenciá-las usam-se `fdisk` (suporta MBR e, nas versões atuais, GPT), `gdisk` (focado em GPT) e `parted`.

### 1.5 Recursos de hardware (endereçamento)

| Recurso | O que é | Onde consultar |
|---|---|---|
| **IRQ** (*Interrupt Request*) | Canal pelo qual o dispositivo "avisa" a CPU que precisa de atenção. 0–15 nos sistemas antigos; hoje gerenciado via APIC | `/proc/interrupts` |
| **DMA** (*Direct Memory Access*) | Permite ao dispositivo transferir dados direto para a RAM, sem passar pela CPU | `/proc/dma` |
| **Portas de E/S** (*I/O ports (Input/Output)*) | Faixas de endereço de E/S (Entradas/Saídas) usadas na comunicação CPU ↔ dispositivo | `/proc/ioports` |
| **Memória mapeada** (*memory-mapped I/O*) | Região de memória reservada para comunicação com o dispositivo | `/proc/iomem` |

> [!NOTE]
> IRQ = *Interrupt ReQuest* (requisição de interrupção). Em PCs modernos o `/proc/dma` costuma estar quase vazio, pois o DMA clássico (ISA) caiu em desuso; os dispositivos modernos fazem *bus mastering* por conta própria.

### 1.6 Dispositivos de bloco × caractere

| Tipo | Como transfere dados | Exemplos | Letra no `ls -l` |
|---|---|---|---|
| **Bloco** | Em **blocos**, com acesso aleatório e uso de buffer/cache pelo kernel | `/dev/sda`, `/dev/nvme0n1`, `/dev/sr0` | `b` |
| **Caractere** | **Byte a byte**, como fluxo, sem blocos | `/dev/tty`, `/dev/null`, `/dev/random`, mouse, portas seriais | `c` |

```bash
$ ls -l /dev/sda /dev/tty
brw-rw---- 1 root disk 8, 0 out 29 10:00 /dev/sda
crw-rw-rw- 1 root tty  5, 0 out 29 10:00 /dev/tty
```

- O **`b`** / **`c`** no início indica o tipo.
- Os números `8, 0` são **major** (identifica o *driver*) e **minor** (identifica o dispositivo/partição). A lista de majors está em `/proc/devices`.

**Convenção de nomes**

| Nome | Dispositivo |
|---|---|
| `/dev/sda`, `/dev/sdb` | Discos SATA/SCSI/SAS e **USB** (pendrives, HDs externos) |
| `/dev/sda1`, `/dev/sda2` | Partições do `sda` |
| `/dev/nvme0n1` | **SSD NVMe** (controlador 0, namespace 1) |
| `/dev/nvme0n1p1` | Partição 1 do NVMe (note o **`p`**) |
| `/dev/vda` | Disco virtio (máquinas virtuais) |
| `/dev/mmcblk0`, `/dev/mmcblk0p1` | Cartão SD/eMMC |
| `/dev/sr0` | Leitor óptico (CD/DVD) |
| `/dev/loop0` | Dispositivo *loop* (arquivo montado como disco) |

### 1.7 Tipos de armazenamento em massa

| Tipo | Característica | Como identificar |
|---|---|---|
| **HDD** | Disco rígido magnético (partes móveis) | `ROTA = 1` no `lsblk` |
| **SSD (SATA)** | Memória flash, interface SATA | `ROTA = 0`, nome `sdX` |
| **NVMe** | Flash sobre PCIe, muito mais rápido | Nome `nvmeXnY` |
| **USB** (pendrive/HD externo) | Removível, hotplug | Aparece como `sdX`; `lsusb`, `lsblk` (coluna `RM`/`TRAN`) |
| **Óptico** | CD/DVD/Blu-ray | `/dev/sr0` |

```bash
lsblk -d -o NAME,SIZE,ROTA,TRAN,TYPE     # ROTA=1 → rotacional (HDD); TRAN mostra sata/usb/nvme
cat /sys/block/sda/queue/rotational      # 1 = HDD, 0 = SSD
```

**Identificadores estáveis:** os nomes `sdX` podem mudar entre boots. Por isso, em `/etc/fstab` prefere-se **UUID**/**LABEL**. Veja-os com `blkid` ou em `/dev/disk/by-uuid/`, `/dev/disk/by-label/`, `/dev/disk/by-id/`, `/dev/disk/by-path/`.

### 1.8 Sistemas de arquivos virtuais e o diretório `/dev`

| Diretório | Tipo | O que expõe |
|---|---|---|
| `/proc` | **procfs** | Informações do kernel e dos **processos** (CPU, memória, IRQs, módulos...) |
| `/sys` | **sysfs** | Árvore de **dispositivos e drivers** do kernel, com atributos |
| `/dev` | **devtmpfs** + udev | Arquivos que representam os **dispositivos** |

**sysfs (`/sys`)**: exporta para o user space a estrutura de dispositivos, barramentos e drivers conhecidos pelo kernel. Subdiretórios importantes:

| Caminho | Conteúdo |
|---|---|
| `/sys/devices` | Hierarquia real de todos os dispositivos |
| `/sys/bus` | Dispositivos organizados por barramento (`pci`, `usb`...) |
| `/sys/class` | Dispositivos organizados por **classe** (`net`, `block`, `input`...) |
| `/sys/block` | Dispositivos de bloco (`sda`, `nvme0n1`...) |
| `/sys/module` | Módulos carregados e seus parâmetros |
| `/sys/firmware` | Informações do firmware (ex.: `efi`) |

> [!NOTE]
> O diretório `/dev` é montado como **devtmpfs**: o próprio kernel cria os nós básicos cedo no boot. O **udev** então ajusta permissões, grupos e cria *symlinks* (como `/dev/disk/by-uuid/...`) conforme as regras.

### 1.9 udev

**udev**: gerenciador de dispositivos em user space (daemon `systemd-udevd`). Recebe **uevents** do kernel e:

1. cria/remove nós em `/dev`;
2. define nome, dono, grupo e permissões;
3. cria links simbólicos persistentes;
4. aciona o carregamento de módulos (via `modprobe` e o `MODALIAS`);
5. executa ações definidas em **regras**.

| Local | Conteúdo |
|---|---|
| `/usr/lib/udev/rules.d/` (ou `/lib/udev/rules.d/`) | Regras **padrão** da distribuição/pacotes |
| `/etc/udev/rules.d/` | Regras **do administrador** (têm precedência sobre as de mesmo nome) |
| `/run/udev/` | Banco de dados e estado em tempo de execução |

Exemplo de regra personalizada (`/etc/udev/rules.d/99-pendrive.rules`):

```
SUBSYSTEM=="block", ATTRS{idVendor}=="0951", ATTRS{idProduct}=="1666", SYMLINK+="meu_pendrive"
```

Recarregar regras: `udevadm control --reload` (e `udevadm trigger` para reaplicar).

### 1.10 D-Bus e hald

- **D-Bus**: barramento de mensagens (IPC) que permite que processos conversem entre si e recebam eventos do sistema (ex.: o gerenciador de arquivos é avisado de que um pendrive foi conectado). Há o barramento do **sistema** (*system bus*) e o da **sessão** do usuário (*session bus*). Para observar: `dbus-monitor`.
- **hald** (*HAL daemon*): serviço antigo de abstração de hardware. Está **obsoleto** e foi substituído pelo **udev** (detecção/nós de dispositivos) em conjunto com **D-Bus** e serviços como `udisks` e `upower`. Ele ainda aparece na lista de objetivos como conceito histórico.

### 1.11 Fluxo de carregamento de um módulo

```
Hardware conectado
        ↓
Kernel detecta o dispositivo e gera um uevent (com MODALIAS)
        ↓
udev recebe o evento
        ↓
udev consulta o banco de aliases (modules.alias) e aciona o modprobe
        ↓
modprobe carrega o módulo necessário (e suas dependências, via modules.dep)
        ↓
Driver assume o controle do dispositivo
        ↓
udev cria/ajusta o(s) nó(s) em /dev (e links simbólicos)
```

> [!NOTE]
> O `modprobe` descobre as dependências lendo o arquivo `modules.dep`, gerado pelo `depmod`, em `/lib/modules/<versão>/`.

## 2. Comandos

### 2.1 Tabela-resumo

| Comando | Função | Opções mais importantes | Exemplo |
|---------|--------|--------------------------|---------|
| `lsmod` | Lista os módulos carregados (lê `/proc/modules`). Colunas: `Module`, `Size`, `Used by` | — | `lsmod` |
| `modinfo` | Mostra informações de um módulo (autor, licença, descrição, parâmetros, dependências) | `-p` parâmetros · `-F <campo>` só um campo (`author`, `license`, `description`, `depends`, `filename`) · `-k <versão>` outro kernel | `modinfo e1000e`<br>`modinfo -p snd_hda_intel` |
| `modprobe` | Carrega módulos **resolvendo dependências**; também remove | `-r` remove · `-a` carrega vários · `-v` verboso · `-n` simula (*dry-run*) · `-c` mostra a configuração · `--show-depends` mostra dependências | `modprobe e1000e`<br>`modprobe -r e1000e` |
| `insmod` | Carrega um `.ko` **direto**, sem resolver dependências (exige caminho) | — | `insmod ./meu_driver.ko` |
| `rmmod` | Remove um módulo, sem resolver dependências | `-f` força · `-v` verboso | `rmmod e1000e` |
| `depmod` | Gera/atualiza `modules.dep` (dependências entre módulos) | `-a` todos os módulos | `depmod -a` |
| `lspci` | Lista dispositivos **PCI/PCIe** | `-k` driver em uso e módulos disponíveis · `-v`/`-vv` detalhes · `-nn` IDs numéricos · `-s <slot>` filtra por slot | `lspci -k` |
| `lsusb` | Lista dispositivos **USB** | `-t` árvore · `-v` detalhes · `-d <VID:PID>` filtra | `lsusb -t` |
| `lsblk` | Lista dispositivos de **bloco** (discos, partições) | `-f` sistema de arquivos/UUID · `-o` colunas · `-a` todos · `-p` caminho completo · `-d` só discos | `lsblk -f` |
| `blkid` | Mostra **UUID**, LABEL e tipo de sistema de arquivos | — | `blkid /dev/sda1` |
| `lshw` | Informações detalhadas de todo o hardware (melhor como root) | `-short` resumo · `-class <classe>` filtra (`network`, `disk`...) | `lshw -short` |
| `lscpu` | Resumo da CPU (modelo, núcleos, cache...) | — | `lscpu` |
| `dmidecode` | Dados do firmware (DMI/SMBIOS): fabricante, memória, BIOS | `-t <tipo>` filtra (ex.: `memory`) | `dmidecode -t memory` |
| `dmesg` | Mensagens do buffer do kernel (detecção de hardware) | `-H` legível · `-w` acompanha em tempo real · `-T` timestamps legíveis | `dmesg -w` |
| `udevadm` | Interage com o udev | `monitor` eventos em tempo real · `info` atributos · `trigger` reenvia eventos · `control --reload` recarrega regras · `test` simula regras | `udevadm monitor` |
| `setpci` | Lê/altera registradores de configuração PCI | — | `setpci -s 00:1f.2 COMMAND` |
| `hwinfo` | Detalha o hardware por categoria (nem sempre instalado) | `--short` resumo | `hwinfo --short` |

Exemplos com *pipe* (ficam fora da tabela por causa do caractere `|`):

```bash
dmesg | grep -i usb          # mensagens do kernel sobre USB
dmesg -w                     # fica acompanhando (conecte um pendrive para ver)
lsmod | grep snd             # módulos de áudio carregados
lspci | grep -i ethernet     # placa de rede
```

### 2.2 `lspci`: lendo a saída

```bash
$ lspci -k
00:1f.2 SATA controller: Intel Corporation 8 Series SATA Controller 1 [AHCI mode]
        Kernel driver in use: ahci
        Kernel modules: ahci
02:00.0 Ethernet controller: Intel Corporation 82579LM Gigabit Network Connection
        Kernel driver in use: e1000e
        Kernel modules: e1000e
```

- `02:00.0` = `barramento:dispositivo.função`
- **`Kernel driver in use`** = o driver que está **de fato** controlando o dispositivo.
- **`Kernel modules`** = módulos que *poderiam* controlá-lo.
- Se não aparecer `Kernel driver in use`, o dispositivo está **sem driver** carregado.
- `lspci -nn` mostra os IDs `[vendor:device]`, úteis para buscar o driver correto.

### 2.3 `lsusb`: lendo a saída

```bash
$ lsusb
Bus 001 Device 004: ID 0951:1666 Kingston Technology DataTraveler
Bus 001 Device 001: ID 1d6b:0002 Linux Foundation 2.0 root hub
```

- `ID 0951:1666` = **ID do fabricante (VID) : ID do produto (PID)**.
- `lsusb -t` mostra a **árvore** (hubs, portas, driver e velocidade).
- `lsusb -v -d 0951:1666` mostra os descritores detalhados (geralmente exige root).

### 2.4 `lsmod`: lendo a saída

```bash
$ lsmod
Module                  Size  Used by
snd_hda_intel          57344  3
snd_hda_codec         151552  2 snd_hda_codec_hdmi,snd_hda_intel
e1000e                286720  0
```

- **Used by**: contagem de usos e lista de módulos que **dependem** deste. Um módulo em uso (contagem > 0) **não** pode ser removido com segurança.

### 2.5 `insmod` × `modprobe` × `rmmod`

| Característica | `insmod` | `modprobe` | `rmmod` |
|---|---|---|---|
| Ação | Carrega | Carrega **e** remove (`-r`) | Remove |
| Resolve dependências | ❌ | ✅ | ❌ (falha se estiver em uso) |
| Argumento | **Caminho** do `.ko` | **Nome** do módulo | Nome do módulo |
| Consulta `modules.dep` | ❌ | ✅ | ❌ |
| Respeita `/etc/modprobe.d/` | ❌ | ✅ | ❌ |
| Uso típico | Testes/desenvolvimento | Uso diário | Remoção simples |

```bash
sudo modprobe e1000e                       # carrega (por nome, com dependências)
sudo modprobe snd_hda_intel power_save=0   # carrega com parâmetro
sudo modprobe -r e1000e                    # remove (com dependências não usadas)
sudo insmod /lib/modules/$(uname -r)/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko
sudo rmmod e1000e
```

> [!WARNING]
> Depois de instalar módulos novos manualmente em `/lib/modules/...`, rode `sudo depmod -a` para atualizar `modules.dep`; do contrário o `modprobe` não os encontra direito.

### 2.6 `udevadm`

```bash
udevadm monitor                       # eventos do kernel e do udev em tempo real
udevadm monitor --udev                # só os eventos já processados pelo udev
udevadm info /dev/sda                 # propriedades do dispositivo
udevadm info -a -n /dev/sda           # atributos de toda a cadeia (úteis p/ escrever regras)
sudo udevadm trigger                  # reenvia eventos (replay / coldplug)
sudo udevadm control --reload         # recarrega as regras
udevadm test /sys/class/block/sda     # simula a aplicação das regras
```

### 2.7 Outros utilitários úteis para identificar hardware

```bash
lscpu                      # CPU
free -h                    # memória
cat /proc/cpuinfo          # detalhes da CPU
cat /proc/meminfo          # detalhes da memória
sudo dmidecode -t bios     # versão da BIOS/UEFI
uname -r                   # versão do kernel em uso (nome da pasta de módulos)
journalctl -k              # mensagens do kernel via systemd (equivale ao dmesg)
```

## 3. Configuração de módulos

### 3.1 Onde configurar

| Arquivo/diretório | Função |
|---|---|
| `/etc/modprobe.d/*.conf` | Configuração **do modprobe**: opções, blacklist, aliases, comandos `install`/`remove` |
| `/etc/modules-load.d/*.conf` | Lista de módulos a **carregar no boot** (um por linha) — *systemd* |
| `/etc/modprobe.conf` | Arquivo **antigo**, substituído pelo diretório `modprobe.d` |
| `/lib/modules/<versão>/modules.dep` | Dependências (gerado pelo `depmod`) |
| `/lib/modules/<versão>/modules.alias` | Mapa `alias → módulo` (usado pelo udev/modprobe) |

### 3.2 Diretivas de `/etc/modprobe.d/*.conf`

```
# Impede o carregamento AUTOMÁTICO (por alias) do módulo
blacklist nouveau

# Define parâmetros para o módulo
options snd_hda_intel power_save=0

# Cria um apelido
alias eth-lan e1000e

# Executa um comando no lugar do carregamento normal (bloqueio efetivo)
install bluetooth /bin/false

# Executa um comando ao remover
remove meumodulo /sbin/meu-script-de-limpeza
```

> [!WARNING] `blacklist` não é bloqueio total
> `blacklist` só impede o carregamento **automático por alias**. O módulo ainda pode ser carregado **manualmente** (`modprobe nome`) ou **como dependência** de outro módulo. Para bloqueio efetivo, use `install <módulo> /bin/false`. Em muitas distribuições é necessário regenerar o initramfs (`update-initramfs -u` no Debian/Ubuntu, `dracut -f` no Fedora/RHEL) para que a mudança valha já no início do boot.

### 3.3 Carregar módulo automaticamente no boot

```bash
echo "vfat" | sudo tee /etc/modules-load.d/vfat.conf
```

### 3.4 Passar parâmetros ao kernel/módulo

- Em tempo de carga: `modprobe modulo parametro=valor`
- Permanente: `options modulo parametro=valor` em `/etc/modprobe.d/`
- Módulos *built-in*: na linha de comando do kernel (GRUB), no formato `modulo.parametro=valor`

## 4. Pastas e arquivos

### 4.1 Informações de hardware

| Caminho | Função |
|---|---|
| `/dev` | Arquivos que representam dispositivos (criados dinamicamente pelo `udev`/`devtmpfs`) |
| `/proc` | Sistema de arquivos virtual (**procfs**): informações do kernel e dos processos |
| `/sys` | Sistema de arquivos virtual (**sysfs**): árvore de dispositivos e drivers |
| `/proc/cpuinfo` | Informações da CPU |
| `/proc/meminfo` | Informações da memória RAM |
| `/proc/modules` | Módulos carregados (é o que o `lsmod` lê) |
| `/proc/interrupts` | **IRQs** em uso |
| `/proc/ioports` | **Portas de E/S** registradas |
| `/proc/iomem` | **Memória mapeada** de dispositivos |
| `/proc/dma` | **Canais DMA** em uso |
| `/proc/devices` | Dispositivos de bloco e caractere registrados (números **major**) |
| `/proc/partitions` | Partições conhecidas pelo kernel |
| `/proc/bus/pci/` | Dados dos dispositivos PCI |
| `/sys/bus/usb/devices/` | Dispositivos USB (substitui o antigo `/proc/bus/usb/`) |
| `/dev/bus/usb/` | Nós dos dispositivos USB |
| `/dev/disk/by-uuid/`, `by-label/`, `by-id/`, `by-path/` | Nomes **persistentes** de discos/partições |

> [!NOTE]
> O antigo `/proc/bus/usb/` (usbfs) foi **removido/desativado** nos sistemas atuais. Hoje use `/sys/bus/usb/devices/` e o comando `lsusb`.

### 4.2 Módulos e udev

| Caminho | Função |
|---|---|
| `/lib/modules/<versão-do-kernel>/` | Módulos (`.ko`) do kernel e arquivos `modules.dep`, `modules.alias` |
| `/etc/modprobe.d/` | Configuração persistente dos módulos (blacklist, options, alias, install) |
| `/etc/modules-load.d/` | Módulos a carregar automaticamente no boot |
| `/etc/modprobe.conf` | Arquivo antigo (obsoleto) |
| `/sys/module/<módulo>/parameters/` | Valores atuais dos parâmetros do módulo |
| `/etc/udev/rules.d/` | Regras udev do administrador |
| `/usr/lib/udev/rules.d/` (ou `/lib/udev/rules.d/`) | Regras udev padrão do sistema |

## 6. Armadilhas comuns na prova

1. **`lsmod` lê `/proc/modules`**, e não `/sys/module`.
2. **`modprobe` × `insmod`:** só o `modprobe` resolve dependências e usa o **nome** do módulo; o `insmod` exige o **caminho do `.ko`**.
3. **`rmmod` não resolve dependências:** falha se o módulo estiver em uso (`Used by` > 0).
4. **`lspci` × `lsusb`:** PCI/PCIe × USB. Para o **driver em uso** de um dispositivo PCI, `lspci -k`.
5. **`blacklist` não impede** carregamento manual nem por dependência; `install ... /bin/false` impede.
6. **`/etc/modprobe.conf` é antigo;** o atual é **`/etc/modprobe.d/`**.
7. **`/etc/modules-load.d/`** carrega módulos **no boot**; **`/etc/modprobe.d/`** só **configura** (não carrega por si só).
8. **`/proc/bus/usb/`** é obsoleto; use `/sys/bus/usb/` e `lsusb`.
9. **`hald` está obsoleto;** foi substituído por **udev** + **D-Bus**.
10. **`/dev`** é gerenciado por **udev** (sobre devtmpfs), e **não** é mantido manualmente.
11. **Bloco (`b`) × caractere (`c`):** `/dev/sda` é bloco; `/dev/tty` é caractere.
12. **NVMe:** partições são `nvme0n1p1` (com **`p`**), e não `nvme0n1`1.
13. **Coldplug × hotplug:** o USB é **hotplug**; CPU e RAM são **coldplug**.
14. **`dmesg` pode exigir root** em sistemas com `kernel.dmesg_restrict=1`.
15. **`depmod -a`** deve ser rodado após adicionar módulos manualmente.
16. **`/proc/interrupts` = IRQ**, **`/proc/ioports` = E/S**, **`/proc/iomem` = memória mapeada**, **`/proc/dma` = DMA**.
17. **MBR × GPT** é particionamento (disco); **BIOS × UEFI** é firmware (placa-mãe). Não confundir.
18. **`udevadm trigger`** reenvia eventos; **`udevadm monitor`** apenas observa.

## 7. Laboratório prático

Faça em uma VM ou máquina de testes.

```bash
# 1. Que dispositivos PCI existem e que drivers usam?
lspci -k

# 2. Dispositivos USB e árvore
lsusb
lsusb -t

# 3. Discos, partições, tipo (HDD/SSD) e UUID
lsblk -f
lsblk -d -o NAME,SIZE,ROTA,TRAN
blkid

# 4. Módulos carregados e detalhes de um deles
lsmod | head
modinfo $(lsmod | awk 'NR==2{print $1}')

# 5. Dependências e parâmetros
modprobe --show-depends snd_hda_intel
modinfo -p snd_hda_intel

# 6. Recursos de hardware
cat /proc/interrupts
cat /proc/ioports
cat /proc/iomem
cat /proc/dma
cat /proc/devices

# 7. Tipo de arquivo em /dev
ls -l /dev/sda /dev/tty /dev/null

# 8. Boot em UEFI ou BIOS?
ls /sys/firmware/efi 2> /dev/null && echo UEFI || echo BIOS

# 9. Acompanhar eventos: rode e CONECTE um pendrive em outro terminal
udevadm monitor
dmesg -w

# 10. Testar carga/remoção de módulo inofensivo (ex.: dummy)
sudo modprobe dummy
lsmod | grep dummy
ip link | grep dummy
sudo modprobe -r dummy

# 11. Criar um blacklist de teste
echo "blacklist dummy" | sudo tee /etc/modprobe.d/teste.conf
sudo modprobe dummy && lsmod | grep dummy     # manual ainda carrega!
sudo modprobe -r dummy
sudo rm /etc/modprobe.d/teste.conf
```

## 8. Exercícios de revisão

**1. Qual é a diferença entre um dispositivo coldplug e um hotplug? Dê um exemplo de cada.**
> **Resposta:** Dispositivos **coldplug** só podem ser conectados/removidos com o equipamento desligado e são enumerados no boot (ex.: CPU, RAM). Dispositivos **hotplug** podem ser conectados/removidos com o sistema ligado e são detectados dinamicamente pelo kernel e pelo udev (ex.: pendrive USB).

**2. Qual comando você usaria para descobrir qual driver está sendo usado por uma placa de rede PCI?**
> **Resposta:** `lspci -k`. A linha **`Kernel driver in use`** mostra o driver em uso e **`Kernel modules`** os módulos possíveis.

**3. Qual comando lista os módulos atualmente carregados no kernel, e qual arquivo em `/proc` ele lê?**
> **Resposta:** `lsmod`, que lê `/proc/modules`.

**4. Qual a diferença prática entre `modprobe` e `insmod`?**
> **Resposta:** O `modprobe` recebe o **nome** do módulo e resolve dependências automaticamente (usando `modules.dep`); o `insmod` carrega diretamente o arquivo `.ko` (informado pelo **caminho**), **sem** resolver dependências.

**5. Você quer remover o módulo `e1000e` do kernel de forma segura (com resolução de dependências). Qual comando usar?**
> **Resposta:** `modprobe -r e1000e`.

**6. Onde você consultaria, no `/proc`, os canais de IRQ atualmente em uso?**
> **Resposta:** `/proc/interrupts`.

**7. O que é o `udev` e qual sua relação com o `/dev`?**
> **Resposta:** É o gerenciador de dispositivos em user space que recebe os eventos do kernel e gerencia dinamicamente os arquivos de dispositivo em `/dev`, criando e removendo nós, definindo permissões e links simbólicos e acionando o carregamento de módulos.

**8. Qual comando mostra, em tempo real, os eventos gerados quando você conecta um pendrive USB?**
> **Resposta:** `udevadm monitor` (também é possível acompanhar com `dmesg -w`).

**9. Qual é a diferença entre um dispositivo de bloco e um dispositivo de caractere? Dê um exemplo de cada.**
> **Resposta:** O de **bloco** transfere dados em blocos, com acesso aleatório e uso de buffer/cache (ex.: `/dev/sda`, `b` no `ls -l`). O de **caractere** transfere dados **byte a byte**, como um fluxo (ex.: `/dev/tty`, `c` no `ls -l`).

**10. Qual arquivo/diretório é usado para configurar de forma persistente opções e blacklist de módulos do kernel?**
> **Resposta:** `/etc/modprobe.d/` (arquivos `*.conf`).

**11. Qual arquivo mostra as faixas de memória mapeadas por dispositivos?**
> **Resposta:** `/proc/iomem`. (`/proc/ioports` mostra as **portas de E/S**.)

**12. Como o `modprobe` sabe quais módulos precisam ser carregados antes de outro?**
> **Resposta:** Pelo arquivo `modules.dep`, em `/lib/modules/<versão>/`, gerado pelo `depmod`.

**13. Qual é a diferença entre `blacklist` e `install <módulo> /bin/false` em `/etc/modprobe.d/`?**
> **Resposta:** `blacklist` só impede o carregamento **automático por alias**; o módulo ainda pode ser carregado manualmente ou como dependência. `install <módulo> /bin/false` substitui o carregamento por um comando que falha, bloqueando o módulo de forma efetiva.

**14. Como listar os parâmetros que um módulo aceita?**
> **Resposta:** `modinfo -p <módulo>`. Os valores atuais ficam em `/sys/module/<módulo>/parameters/`.

**15. Como saber se o sistema foi iniciado em modo UEFI?**
> **Resposta:** Verificando se o diretório `/sys/firmware/efi` existe.

**16. Qual o nome do arquivo de dispositivo da primeira partição do primeiro SSD NVMe?**
> **Resposta:** `/dev/nvme0n1p1`.

**17. Como descobrir se um disco é HDD (rotacional) ou SSD?**
> **Resposta:** `lsblk -d -o NAME,ROTA` (`ROTA=1` é HDD, `0` é SSD) ou `cat /sys/block/<disco>/queue/rotational`.

**18. O que substituiu o `hald` no gerenciamento dinâmico de dispositivos?**
> **Resposta:** O **udev**, em conjunto com o **D-Bus** (e serviços como `udisks`/`upower`).

**19. Qual comando exibe os dispositivos USB em forma de árvore, com hubs e portas?**
> **Resposta:** `lsusb -t`.

**20. O que significa `ID 0951:1666` na saída do `lsusb`?**
> **Resposta:** Os IDs de **fabricante (VID)** e de **produto (PID)** do dispositivo, no formato `VID:PID`.
